# pAIr 테이블 정의서

> DB: PostgreSQL + pgvector(벡터 확장, 같은 DB) · 테이블 38개 · 외래 키 59개 · 기준 파일: [pair_schema.sql](pair_schema.sql)
> 표기: **PK** 기본키, **FK** 외래키(→ 참조 테이블), **UQ** 유니크, **NULL** 허용이면 "O"
> 공통: `BIGSERIAL` PK는 1부터 자동 증가하는 번호. 시각은 모두 `TIMESTAMPTZ`(시간대 포함), 기본값 `now()`는 행을 만든 순간.

---

## 1. 회원 · 과제

### companies (회사)
실전 시험을 여는 기업. 회사마다 데이터를 분리하는 기준이다(멀티테넌시). 기업 담당자는 자기 회사의 회차와 응시 결과만 볼 수 있다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| company_id | BIGSERIAL | PK | | 자동 증가 | 회사 번호 |
| name | VARCHAR(100) | | | | 회사 이름 |
| business_no | VARCHAR(20) | UQ | O | | 사업자등록번호. 같은 회사를 두 번 등록하지 못하게 한다. 시연용 회사는 비워 둘 수 있다 |
| created_at | TIMESTAMPTZ | | | now() | 등록 시각 |

**회사 데이터 분리 방법:** 회사를 직접 가리키는 테이블은 users(담당자), exam_sessions(회차), 그리고 가입 과정의 company_inquiries·company_invites뿐이다. 대상자, 응시, 감독 이벤트, 채점 결과는 회차를 따라가면 회사가 정해지므로 company_id를 중복해서 두지 않는다(3정규형). 기업 담당자의 모든 조회는 "로그인한 담당자의 company_id = 회차의 company_id" 조건을 거친다.

### users (회원)
로그인하고 응시 기록을 남기는 사람. 직군은 두지 않는다(직군은 과제의 성질이고, 어느 직군 과제든 풀 수 있다).

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| user_id | BIGSERIAL | PK | | 자동 증가 | 회원 번호. 다른 테이블이 회원을 가리킬 때 쓴다. 이메일은 바뀔 수 있어 PK로 쓰지 않는다 |
| email | VARCHAR(255) | UQ | | | 로그인 ID. 같은 이메일로 두 번 가입할 수 없다 |
| password_hash | VARCHAR(100) | | | | 비밀번호를 BCrypt로 바꾼 값(60자). 원문은 저장하지 않는다 |
| name | VARCHAR(50) | | | | 화면에 보이는 이름 |
| role | VARCHAR(10) | | | `'USER'` | 권한(CHECK). `USER` 일반 응시자, **`MANAGER` 기업 매니저**(회차 만들기, 기업용 과제 고르기, 대상자 등록, 결과 보기, 감독관 초대), **`PROCTOR` 기업 감독관**(맡은 회사 회차의 감독 화면과 감독 이벤트 판단만), `ADMIN` 채점 툴과 전체 관리 |
| company_id | BIGINT | FK → companies | O | | 소속 회사. **`MANAGER`·`PROCTOR`만 있고 그 외에는 비어 있다**(`(role IN ('MANAGER','PROCTOR')) = (company_id IS NOT NULL)` 검사). 응시자는 회사에 속하지 않는다(여러 회사의 시험을 볼 수 있으므로) |
| created_at | TIMESTAMPTZ | | | now() | 가입 시각 |
| deleted_at | TIMESTAMPTZ | | O | | 탈퇴 시각. 탈퇴하면 행을 지우지 않고 **개인정보만 익명값으로 바꾼다**: 이메일 `deleted-<id>@deleted.pair.invalid`, 이름 "탈퇴 회원", 비밀번호 해시 `!`(로그인 불가). 응시·채점 기록과 크레딧 원장은 통계와 정산을 위해 남는다 |

**기업 회원 가입:** 자체 가입은 없다. **도입 문의(company_inquiries) → 관리자 승인(회사 등록) → 관리자가 첫 `MANAGER` 초대(company_invites) → 초대 링크로 가입** 순서다. 이후 그 회사 `MANAGER`가 자기 회사 `PROCTOR`를 초대한다. 한 회사에 매니저와 감독관을 여러 명 둘 수 있다.

### company_inquiries (기업 도입 문의)
기업이 사이트의 문의 폼으로 낸 도입 신청. 관리자가 승인하면 회사를 등록하고 company_id를 채운다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| inquiry_id | BIGSERIAL | PK | | 자동 증가 | 문의 번호 |
| company_name | VARCHAR(100) | | | | 회사 이름 |
| business_no | VARCHAR(20) | | | | 사업자등록번호. 거절 후 다시 문의할 수 있어 UQ를 걸지 않는다 |
| contact_name | VARCHAR(50) | | | | 담당자 이름 |
| contact_email | VARCHAR(255) | | | | 담당자 이메일. 승인되면 이 주소로 초대 메일이 간다 |
| message | TEXT | | O | | 문의 내용 |
| status | VARCHAR(10) | | | `'PENDING'` | `PENDING` 대기, `APPROVED` 승인, `REJECTED` 거절 |
| company_id | BIGINT | FK → companies | O | | 승인하며 등록한 회사. **승인일 때만** 있다(`(status = 'APPROVED') = (company_id IS NOT NULL)`) |
| handled_by | BIGINT | FK → users | O | | 처리한 관리자. 대기 중이면 비어 있다(CHECK) |
| handled_at | TIMESTAMPTZ | | O | | 처리 시각. handled_by와 함께 있거나 함께 비어 있다(CHECK) |
| created_at | TIMESTAMPTZ | | | now() | 문의 시각 |

### company_invites (기업 담당자 초대)
기업 회원(매니저·감독관) 초대. 초대 링크로만 기업 회원 계정을 만들 수 있다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| invite_id | BIGSERIAL | PK | | 자동 증가 | 초대 번호 |
| company_id | BIGINT | FK → companies | | | 어느 회사 담당자로 초대했는지 |
| email | VARCHAR(255) | | | | 초대 이메일. 가입하는 계정의 이메일과 같아야 한다(서비스 코드에서 검사) |
| role | VARCHAR(10) | | | | 가입할 권한. `MANAGER` 또는 `PROCTOR`(CHECK). 가입한 계정의 role이 이 값이 된다 |
| token_hash | CHAR(64) | UQ | | | 초대 링크 토큰의 SHA-256 해시. 원문은 메일에만 있다 |
| invited_by | BIGINT | FK → users | | | 초대한 회원. 관리자는 누구든 초대할 수 있고, `MANAGER`는 **같은 회사의 `PROCTOR`만** 초대할 수 있다(서비스 코드에서 검사) |
| expires_at | TIMESTAMPTZ | | | | 만료 시각(예: 7일). `expires_at > created_at` 검사. 만료되면 새로 초대한다(새 행) |
| accepted_user_id | BIGINT | FK → users, UQ | O | | 초대로 가입한 담당자. 초대 하나로 계정 하나만 만든다 |
| accepted_at | TIMESTAMPTZ | | O | | 가입 시각. accepted_user_id와 함께 있거나 함께 비어 있다(CHECK) |
| created_at | TIMESTAMPTZ | | | now() | 초대 시각 |

### credit_purchases (크레딧 구매)
자가진단 크레딧 단품 구매 한 건. 결제는 결제 대행사 테스트 모드로 한다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| purchase_id | BIGSERIAL | PK | | 자동 증가 | 구매 번호(결제 대행사에 보내는 주문 번호) |
| user_id | BIGINT | FK → users | | | 산 회원 |
| credits | INTEGER | | | | 구매 크레딧. `> 0` 검사 |
| amount_krw | INTEGER | | | | 결제 금액(원). `>= 0` 검사 |
| status | VARCHAR(10) | | | `'READY'` | `READY` 결제 전, `PAID` 완료, `FAILED` 실패, `CANCELED` 취소 |
| pg_payment_key | VARCHAR(200) | UQ | O | | 결제 대행사가 준 결제 키. 같은 결제 승인이 두 번 처리되지 않게 UQ |
| created_at | TIMESTAMPTZ | | | now() | 주문 시각 |
| paid_at | TIMESTAMPTZ | | O | | 결제 완료 시각. `PAID`면 결제 키와 함께 반드시 있다(CHECK) |

결제가 완료(`PAID`)되는 순간 credit_ledger에 `PURCHASE` 적립 한 줄을 같은 트랜잭션으로 넣는다.

### tasks (과제)
응시 대상 과제. 과제 목록 카드와 응시 화면의 내용이 여기서 나온다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| task_id | BIGSERIAL | PK | | 자동 증가 | 과제 번호 |
| code | VARCHAR(50) | UQ | | | 사람이 읽는 과제 이름. 예: `order-deadlock`, `pricing-plan`. 주소(URL)에도 쓴다 |
| title | VARCHAR(200) | | | | 제목. 예: "주문 처리 장애 원인 분석" |
| summary | VARCHAR(200) | | | | 과제 목록 카드의 한두 줄 소개. 예: "주문이 3초 넘게 멈췄다가 실패합니다. 잠금 순서와 재고 정합성 문제를 찾아 고치세요." |
| description | TEXT | | | | 응시 화면에 보이는 상세 설명(상황, 배경) |
| requirements | TEXT | | | | 요구사항 목록. 채점 모델도 이 내용을 기준으로 판정한다 |
| track | VARCHAR(10) | | | | 직군. `DEV` 개발, `BIZ` 비개발. 과제 목록의 직군 탭 |
| category | VARCHAR(30) | | | | 과제 형태. 예: 장애 분석, 기능 구현, 기획서, 데이터 해석. 목록의 섹션 구분 |
| difficulty | VARCHAR(10) | | | | 난이도. 예: 초급, 중급, 고급. 카드의 난이도 칩 |
| time_limit_min | INTEGER | | | | 제한 시간(분). 예: 60. 응시 화면 타이머 |
| usage | VARCHAR(10) | UQ(task_id, usage) | | | **용도**(CHECK). `SELF` 자가진단용, `LIVE` 기업 실전용. 과제마다 하나다. 기업용 과제는 자가진단 목록에 절대 나오지 않아 문제가 새지 않는다. 관리자가 기업용 과제를 많이 만들어 두면 기업 담당자가 골라 회차에 건다(모든 기업이 공유). (task_id, usage) UQ는 응시와 회차 과제가 용도를 FK로 검사하려고 둔다 |
| status | VARCHAR(20) | | | `'CLOSED'` | 공개 상태(CHECK). `OPEN` 공개(응시 가능), `CLOSED` 숨김(응시자에게 안 보임). 새 과제와 AI가 만든 과제는 숨김으로 시작한다 |
| parent_task_id | BIGINT | FK → tasks | O | | 복제 원본 과제. 응시가 있는 과제는 고치지 않고 복제해서 새 과제로 고친다 |
| created_by | BIGINT | FK → users | | | 만든 관리자 |
| created_at | TIMESTAMPTZ | | | now() | 만든 시각 |
| updated_at | TIMESTAMPTZ | | | now() | 마지막으로 고친 시각 |
| published_at | TIMESTAMPTZ | | O | | 처음 공개한 시각. 비어 있으면 한 번도 공개 안 된 초안. `OPEN`이면 반드시 있어야 한다(CHECK) |

**상태는 두 가지뿐이다:** `CLOSED`(콘솔의 "검수 대기")와 `OPEN`("공개"). 공개를 취소한 과제도 `CLOSED`로 돌아가 검수 대기에 함께 보인다. `published_at`은 처음 공개한 시각 기록으로만 남긴다(2026-11-18).
**수정·삭제 기준:** 상태가 아니라 "응시가 있는가"로 정한다. 응시가 한 건이라도 있으면 고치지 않고 복제(parent_task_id)한다. 예전 응시 기록과 채점 근거가 바뀐 과제를 가리키지 않게 하려는 것이다.

### document_pages (문서 페이지 텍스트)
PDF에서 뽑은 글자를 페이지별로 저장한다. **응시용 AI 어시스턴트**는 이 테이블을 검색하지 않고, 응시자가 고른 페이지(예: "B.pdf 3~5쪽")의 글자만 꺼내 보낸다. 그래서 "여러 문서에서 필요한 부분을 찾는 능력"이 그대로 평가된다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| task_file_id | BIGINT | PK, FK → task_files | | | 어느 PDF의 페이지인지 |
| page_no | INTEGER | PK | | | 페이지 번호(1부터). PDF와 함께 복합 PK |
| text | TEXT | | | | 그 페이지에서 뽑은 글자 |

### document_chunks (문서 조각, 채점용 RAG)
채점 모델이 응시자의 답과 관련된 문서 부분을 의미 검색으로 찾을 때 쓴다(응시용 AI는 쓰지 않는다). 벡터 DB를 따로 두지 않고 같은 PostgreSQL에 pgvector 확장으로 저장해서, 다른 테이블과 실제 외래 키로 연결된다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| chunk_id | BIGSERIAL | PK | | 자동 증가 | 조각 번호 |
| task_file_id | BIGINT | FK → document_pages(task_file_id, page_no), UQ | | | 어느 PDF의 조각인지 |
| page_no | INTEGER | FK → document_pages(task_file_id, page_no), UQ | | | 어느 페이지의 조각인지. 조각은 페이지 경계를 넘지 않게 자른다. 문항 근거 페이지(question_sources.pages)와 비교할 때 쓴다 |
| chunk_no | INTEGER | UQ(task_file_id, page_no, chunk_no) | | | 페이지 안 조각 순서 |
| content | TEXT | | | | 조각 글자. 검색 결과로 채점 모델에 넘긴다. 페이지 글자의 일부라 **의도된 중복(반정규화)**이다. 임베딩과 함께 다시 만드는 파생 데이터라 검색할 때마다 잘라 내지 않도록 함께 둔다 |
| token_count | INTEGER | | | | 조각의 토큰 수. 채점 모델에 넘길 양을 계산할 때 쓴다 |
| embedding | VECTOR(1536) | 인덱스(HNSW, 코사인) | | | 조각의 임베딩 벡터. 1536은 OpenAI 계열 임베딩 기준이고, 임베딩 모델을 확정하면 차원을 맞춘다 |

쓰임: 문항 채점(question_results)에서 응시자 답과 관련된 조각을 찾아 정답 근거 페이지와 대조, 통제력 판정(C2, 자료와 다른 수치)에서 관련 조각만 채점 모델에 넘겨 토큰을 줄인다.

### task_questions (문항)
객관식, 주관식 문항과 제출 후 후속 질문을 한 테이블에 둔다. 문항을 고칠 때는 수정하지 않고 새 행을 추가한다(예전 답변이 바뀐 질문에 붙지 않게).

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|

### credit_ledger (크레딧 원장)
크레딧이 늘거나 준 일 한 건마다 한 줄. 잔액을 덮어쓰지 않고 **원장에 쌓아서** 언제 왜 바뀌었는지 모두 남긴다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| ledger_id | BIGSERIAL | PK | | 자동 증가 | 원장 번호. 같은 회원 안에서 처리 순서 |
| user_id | BIGINT | FK → users | | | 누구의 크레딧인지 |
| amount | INTEGER | | | | 증감. 적립은 +, 사용은 -. 0은 안 된다. 적립 사유(`SIGNUP`, `PURCHASE`)일 때만 양수(CHECK) |
| balance_after | INTEGER | | | | 처리 후 잔액. **`>= 0` 검사로 잔액이 음수가 되는 차감을 DB가 막는다.** 현재 잔액 = 그 회원의 가장 최근 줄 |
| reason | VARCHAR(20) | | | | `SIGNUP` 가입 지급, `PURCHASE` 구매, `ATTEMPT_START` 응시 시작(채점 1회 포함), `ROLLBACK` 롤백으로 새 응시, `CHAT_TURN` AI 채팅 한 턴 |
| purchase_id | BIGINT | FK → credit_purchases, UQ | O | | 구매 적립일 때만(CHECK). UQ라 한 결제가 두 번 적립되지 않는다 |
| attempt_id | BIGINT | FK → attempts, UQ | O | | 응시 시작·롤백일 때만(CHECK). UQ라 한 응시에서 시작 크레딧을 두 번 빼지 않는다. 롤백으로 만든 응시는 `ROLLBACK`으로만 뺀다 |
| turn_id | BIGINT | FK → chat_turns, UQ | O | | 채팅 턴일 때만(CHECK). 응시자(`USER`) 턴 하나에 한 번만 뺀다(UQ) |
| created_at | TIMESTAMPTZ | | | now() | 처리 시각 |

- **사용량은 설정값:** 예) 가입 30, 응시 시작 10, 롤백 5, 채팅 턴 1. 바뀌어도 원장에는 그때 뺀 양이 남는다.
- **동시성:** 차감할 때 `SELECT ... FROM users WHERE user_id = ? FOR UPDATE`로 회원 행을 잠근 뒤 최신 잔액을 읽고 새 줄을 넣는다. 채팅을 연달아 보내도 잔액이 꼬이지 않고, 모자라면 balance_after 검사에서 막힌다.
- **부족할 때:** 응시 중 크레딧이 바닥나면 AI 채팅만 막는다. 편집과 제출은 되고, 채점은 시작 때 이미 냈으므로 항상 된다.
- 실전 응시(`LIVE`)는 크레딧을 쓰지 않는다(기업 과금은 기획만).

답변은 답하는 방식에 따라 두 테이블로 나눈다. 객관식은 "고른 보기"가, 단답형·서술형은 "글 하나"가 답이라 저장할 것이 다르기 때문이다. 어느 테이블에 들어갈지는 문항 유형이 정하고, 두 테이블 모두 `(question_id, question_type)` 복합 외래 키로 task_questions를 가리켜서 **문항의 실제 유형과 다른 테이블에는 답이 들어가지 못한다**(예: 객관식 문항에 글 답변, 단답형 문항에 보기 선택).

### choice_answers (객관식 답변)
응시 ↔ 보기의 다대다 관계 테이블. 고른 보기 하나가 한 행이다. 복수 선택(MULTI)은 고른 만큼 행이 생긴다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| attempt_id | BIGINT | PK, FK → attempts | | | 어느 응시의 답인지 |
| question_id | BIGINT | FK → task_questions(question_id, question_type), FK → question_choices(choice_id, question_id) | | | 어느 문항인지. 보기가 이 문항의 보기인지도 외래 키로 확인한다 |
| question_type | VARCHAR(10) | FK → task_questions(question_id, question_type) | | | `SINGLE` 하나 고르기, `MULTI` 여러 개 고르기(CHECK). 문항의 실제 유형과 같아야만 들어간다 |
| choice_id | BIGINT | PK, FK → question_choices | | | 고른 보기. 응시와 함께 복합 PK라 같은 보기를 두 번 고를 수 없다 |
| answered_at | TIMESTAMPTZ | | | now() | 고른 시각 |

`SINGLE` 문항은 부분 유니크 인덱스(`uq_choice_answers_single`: question_type = 'SINGLE'인 행에서 (attempt_id, question_id) 유일)로 한 응시에 보기를 하나만 고를 수 있다. 보기를 바꾸면 행을 지우고 새로 넣는다.

| attempt_id | BIGINT | FK → attempts, UQ(attempt_id, question_id) | | | 어느 응시의 답인지 |
| question_id | BIGINT | FK → task_questions(question_id, question_type), UQ(attempt_id, question_id) | | | 어느 문항인지. 한 응시에서 같은 문항에 답은 하나 |
| question_type | VARCHAR(10) | FK → task_questions(question_id, question_type) | | | `SHORT` 단답형, `ESSAY` 서술형(CHECK). 문항의 실제 유형과 같아야만 들어간다 |
| content | TEXT | | | | 답변 글. 비어 있으면 안 된다(무응답은 서비스가 정한 표시로 저장) |
| answered_at | TIMESTAMPTZ | | | now() | 답한 시각 |

**question_type을 답변에도 두는 이유:** 문항 테이블에 이미 있는 값이라 중복이지만, 복합 외래 키로 문항과 묶여 있어 다른 값은 들어갈 수 없다(정합성이 보장되는 반정규화). 이 컬럼 덕분에 "유형에 맞는 테이블에만 답이 들어간다"를 DB가 직접 지킨다.

**DB로 못 막는 것(서비스 코드에서 지킴):** 한 문항에 객관식 답변과 글 답변이 둘 다 생기는 것은 유형 외래 키 때문에 실제로는 생길 수 없지만, "객관식 문항인데 보기를 하나도 안 고름(미응답)"은 행이 없는 상태라 DB가 알 수 없다. 제출할 때 서비스가 검사한다.

## 6. 실전 시험 · 감독

실전 응시(attempts.mode = `LIVE`)에서만 쓴다. 자가진단(`SELF`)은 회차와 감독 없이 응시한다.
회차에는 과제를 여러 개 건다. 대상자는 한 번 입장해 감독 동의를 한 번 하고, 과제마다 응시를 1건씩 만든다. 시간은 과제별이 아니라 회차 전체(시작~종료)로 보고, 그 안에서 과제를 자유롭게 오간다. 종료 시각에 모든 과제가 함께 자동 제출된다.
응시자는 회원가입 없이 **메일로 받은 개인별 입장 링크로만** 들어온다(회차 공용 입장 코드는 두지 않는다, 2026-11-18). 링크는 기업이 등록한 명단의 대상자에게만 발급되므로 명단에 없는 사람은 입장할 수 없다.
감독 영상은 서버로 보내지 않는다. 브라우저에서 분석하고, 이상이 생긴 순간의 이벤트와 스냅샷 1장만 저장한다. 얼굴로 사람을 식별하지 않으므로(얼굴이 있는지, 몇 개인지만 봄) 생체인식정보를 저장하지 않는다.

| sort_order | SMALLINT | UQ(session_id, sort_order) | | | 응시 화면에 보여 줄 순서(1부터). `sort_order > 0` 검사 |

### exam_participants (회차 응시 대상자)
회차에 초대한 사람. 실전 시험은 **로그인 없이** 응시하므로 회원과 연결하지 않고, 기업이 등록한 이메일과 이름으로 응시자를 구분한다. 응시 기록은 기업 쪽에만 남고 응시자의 "내 기록"에는 나오지 않는다(2026-11-18, 예전 user_id 컬럼 삭제).

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| participant_id | BIGSERIAL | PK | | 자동 증가 | 대상자 번호 |
| session_id | BIGINT | FK → exam_sessions, UQ(session_id, email) | | | 어느 회차의 대상자인지 |
| email | VARCHAR(255) | UQ(session_id, email) | | | 초대 메일 주소. 같은 회차에 같은 사람을 두 번 초대할 수 없다 |
| name | VARCHAR(50) | | | | 기업이 등록한 이름 |
| invite_token_hash | CHAR(64) | UQ | | | 메일 입장 링크(`/entry?invite=<토큰>`) 토큰의 **SHA-256 해시**. 토큰 원문(`SecureRandom` 32바이트, Base64URL)은 메일에만 있고 DB에는 해시만 둔다. DB가 유출돼도 링크를 만들 수 없다. 들어오면 받은 토큰을 해시해서 찾는다. **유일한 입장 방법**이라 링크만으로 본인을 인식한다. 만료 시각은 따로 없고 회차 종료가 지나면 쓸 수 없다. 메일을 다시 보내면 토큰을 새로 만든다(이전 링크 무효). 시험 중 끊기면 같은 링크로 다시 들어와 이어 푼다 |
| invited_at | TIMESTAMPTZ | | | now() | 초대 메일 발송 시각. 대상자 등록(CSV 업로드) 즉시 보내고, 다시 보내면 갱신한다 |
| reminded_at | TIMESTAMPTZ | | O | | 시작 24시간 전 알림 메일 발송 시각. 비어 있으면 아직 안 보냄(알림 배치가 이 값으로 중복 발송을 막는다) |
| entered_at | TIMESTAMPTZ | | O | | 입장 시각. 비어 있으면 미입장(관리자 화면의 "미응시") |

대상자의 응시는 attempts.participant_id로 찾는다(대상자 1 : 응시 N, 회차 과제마다 1건). 예전에는 대상자가 attempt_id 하나만 가졌지만 과제를 여러 개 주려고 방향을 바꿨다(2026-11-18).

### proctor_consents (감독 동의 · 환경 점검)
입장할 때 받는 카메라 사용 동의와 환경 점검 결과. 과제가 여러 개여도 대상자마다 회차당 한 번만 받으므로 participant_id가 PK다(1:1).

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| participant_id | BIGINT | PK, FK → exam_participants | | | 어느 대상자의 동의인지 |
| consent_version | VARCHAR(20) | | | | 동의서 버전. 문구가 바뀌어도 누가 어느 문구에 동의했는지 남는다 |
| env_check | JSONB | | | | 환경 점검 결과. 예: `{"camera": true, "fullscreen": true, "browser": "Chrome 142"}` |
| consented_at | TIMESTAMPTZ | | | now() | 동의 시각 |

### proctor_events (감독 이벤트)
부정행위로 의심되는 순간 하나. 리포트의 "주의 구간"과 관리자 화면에 표시한다. 자동 탈락이 아니라 사람이 판단하도록 보여 주는 기록이다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| proctor_event_id | BIGSERIAL | PK | | 자동 증가 | 감독 이벤트 번호 |
| attempt_id | BIGINT | FK → attempts | | | 어느 응시에서 생긴 이벤트인지 |
| type | VARCHAR(20) | | | | 종류(CHECK). 브라우저: `TAB_HIDDEN` 탭 전환, `WINDOW_BLUR` 창 이탈, `PASTE` 외부 붙여넣기, `FULLSCREEN_EXIT` 전체화면 이탈. 카메라: `NO_FACE` 얼굴 없음, `MULTI_FACE` 여러 얼굴, `HEAD_TURN` 고개 돌림, `PHONE` 휴대폰 |
| started_at | TIMESTAMPTZ | | | | 시작 시각 |
| duration_ms | INTEGER | | | 0 | 지속 시간(ms). 붙여넣기처럼 순간인 이벤트는 0. 0 이상 검사 |
| confidence | NUMERIC(4,3) | | O | | 카메라 감지 모델의 확신도(0~1). 브라우저 이벤트는 확실하므로 비어 있다. 관리자 화면에서 낮은 확신도는 흐리게 보여 오탐을 줄인다 |
| detail | JSONB | | O | | 종류마다 다른 상세. 예: 붙여넣기 `{"chars": 840, "fromAssistant": false}`, 고개 돌림 `{"yawDeg": 48}` |
| snapshot_key | VARCHAR(255) | | O | | 그 순간의 카메라 스냅샷 저장 위치(파일 저장소 경로). 카메라 이벤트만 있다 |
| snapshot_deleted_at | TIMESTAMPTZ | | O | | 보관 기간이 지나 스냅샷을 지운 시각. 이벤트 기록은 남기고 사진만 지운다 |
| review | VARCHAR(10) | | O | | 담당자 판단. `OK` 문제 없음, `SUSPECT` 부정 의심. 비어 있으면 아직 확인하지 않은 이벤트(콘솔의 "미확인") |
| review_note | TEXT | | O | | 판단 메모. 예: "화면 공유 끊김, 응시자 문의로 확인" |
| reviewed_by | BIGINT | FK → users | O | | 판단한 회원. **같은 회사 `PROCTOR`** 또는 관리자만(서비스 코드에서 검사) |
| reviewed_at | TIMESTAMPTZ | | O | | 판단 시각. review, reviewed_by, reviewed_at은 셋 다 있거나 셋 다 없다(CHECK). 다시 판단하면 덮어쓴다 |

**attempt_events(작업 기록)와 따로 둔 이유:** 작업 기록은 채점에 쓰는 응시자의 작업이고, 감독 이벤트는 채점과 무관한 부정행위 의심 기록이다. 보는 사람(채점 모델 / 기업 담당자)과 보관 기간(영구 / 스냅샷은 기간 후 삭제)이 달라서 분리했다. 붙여넣기는 채점에도 쓰일 수 있지만, 우리 어시스턴트 답에서 복사한 붙여넣기(`fromAssistant: true`)는 감독 이벤트로 남기지 않는다.

## 7. 문제 생성

관리자가 AI로 만든 과제는 별도 테이블 없이 tasks 이하 테이블(과제 파일, 문항, 보기, 정답, 근거 문서)에 **숨김(CLOSED)으로** 바로 들어간다. 관리자가 검수·수정한 뒤 공개(OPEN)한다. 검수 전 초안은 `status = 'CLOSED' AND published_at IS NULL`인 과제다. 생성 프롬프트와 생성 요청 기록(정의, 토큰, 실패 이유)은 DB에 남기지 않는다.

## 조회용 인덱스

PostgreSQL 은 외래 키에 인덱스를 자동으로 만들지 않는다. 화면에서 자주 따라가는 외래 키 10개에만 건다. UNIQUE 나 복합 PK 의 첫 컬럼인 외래 키(`chat_turns.attempt_id`, `check_results.scoring_id` 등)는 그 인덱스를 함께 쓰므로 따로 만들지 않는다. 나머지 외래 키는 데이터가 적은 기준 테이블 쪽이거나 거의 조회하지 않아 넣지 않았다.

| 인덱스 | 컬럼 | 쓰는 곳 |
|---|---|---|
| idx_attempts_user_id | attempts.user_id | 내 응시 목록 |
| idx_attempt_events_attempt_id | attempt_events.attempt_id | 응시 작업 기록 |
| idx_checkpoints_attempt_id | checkpoints.attempt_id | 복기 트리 |
| idx_chat_attachments_turn_id | chat_attachments.turn_id | 대화의 첨부 |
| idx_scorings_attempt_id | scorings.attempt_id | 리포트 |
| idx_judge_calls_scoring_id | judge_calls.scoring_id | 채점 토큰 집계 |
| idx_judge_verdicts_result_id | judge_verdicts.result_id | 리포트(체크별 모델 판정) |
| idx_exam_sessions_company_id | exam_sessions.company_id | 회사의 회차 목록(관리자 화면) |
