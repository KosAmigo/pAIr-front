# pAIr 테이블 정의서

> DB: PostgreSQL + pgvector(벡터 확장, 같은 DB) · 테이블 33개 · 외래 키 46개 · 기준 파일: [pair_schema.sql](pair_schema.sql)
> 표기: **PK** 기본키, **FK** 외래키(→ 참조 테이블), **UQ** 유니크, **NULL** 허용이면 "O"
> 공통: `BIGSERIAL` PK는 1부터 자동 증가하는 번호. 시각은 모두 `TIMESTAMPTZ`(시간대 포함), 기본값 `now()`는 행을 만든 순간.

## 1. 회원 · 과제

### companies (회사)
실전 시험을 여는 기업. 회사마다 데이터를 분리하는 기준이다(멀티테넌시). 기업 담당자는 자기 회사의 회차와 응시 결과만 볼 수 있다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| company_id | BIGSERIAL | PK | | 자동 증가 | 회사 번호 |
| name | VARCHAR(100) | | | | 회사 이름 |
| business_no | VARCHAR(20) | UQ | O | | 사업자등록번호. 같은 회사를 두 번 등록하지 못하게 한다. 시연용 회사는 비워 둘 수 있다 |
| created_at | TIMESTAMPTZ | | | now() | 등록 시각 |

**회사 데이터 분리 방법:** 회사를 직접 가리키는 테이블은 users(담당자)와 exam_sessions(회차) 둘뿐이다. 대상자, 응시, 감독 이벤트, 채점 결과는 회차를 따라가면 회사가 정해지므로 company_id를 중복해서 두지 않는다(3정규형). 기업 담당자의 모든 조회는 "로그인한 담당자의 company_id = 회차의 company_id" 조건을 거친다.

### users (회원)
로그인하고 응시 기록을 남기는 사람. 직군은 두지 않는다(직군은 과제의 성질이고, 어느 직군 과제든 풀 수 있다).

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| user_id | BIGSERIAL | PK | | 자동 증가 | 회원 번호. 다른 테이블이 회원을 가리킬 때 쓴다. 이메일은 바뀔 수 있어 PK로 쓰지 않는다 |
| email | VARCHAR(255) | UQ | | | 로그인 ID. 같은 이메일로 두 번 가입할 수 없다 |
| password_hash | VARCHAR(100) | | | | 비밀번호를 BCrypt로 바꾼 값(60자). 원문은 저장하지 않는다 |
| name | VARCHAR(50) | | | | 화면에 보이는 이름 |
| role | VARCHAR(10) | | | `'USER'` | 권한. `USER` 일반 응시자, `COMPANY` 기업 담당자(실전 시험 회차를 만들고 결과·감독 이벤트 확인), `ADMIN` 채점 툴과 전체 관리 |
| company_id | BIGINT | FK → companies | O | | 소속 회사. 기업 담당자(`COMPANY`)만 있다. 응시자는 회사에 속하지 않는다(여러 회사의 시험을 볼 수 있으므로). `COMPANY`인데 비어 있으면 막는다(CHECK) |
| created_at | TIMESTAMPTZ | | | now() | 가입 시각 |

| category | VARCHAR(30) | | | | 과제 형태. 예: 장애 분석, 기능 구현, 기획서, 데이터 해석. 목록의 섹션 구분 |
| difficulty | VARCHAR(10) | | | | 난이도. 예: 초급, 중급, 고급. 카드의 난이도 칩 |

### task_files (과제 파일)
과제가 응시자에게 주는 자료와, 응시자에게 숨기는 채점용 파일.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| task_file_id | BIGSERIAL | PK | | 자동 증가 | 파일 번호 |
| task_id | BIGINT | FK → tasks, UQ(task_id, path) | | | 어느 과제의 파일인지 |
| path | VARCHAR(255) | UQ(task_id, path) | | | 파일 경로. 예: `src/shop/OrderService.java`, `자료/요금제별_매출.csv`. 한 과제 안에서 같은 경로는 하나 |
| content | TEXT | | O | | 텍스트 파일(코드, 마크다운, CSV)의 내용. PDF는 비워 둔다 |
| storage_key | VARCHAR(500) | | O | | PDF 같은 바이너리 파일이 저장된 위치(서버 경로나 S3 키). 텍스트 파일은 비워 둔다 |
| mime_type | VARCHAR(100) | | | | 파일 형식. 예: `text/x-java`, `application/pdf` |

| visibility | VARCHAR(10) | | | | `VISIBLE` 응시자에게 보임, `HIDDEN` 숨김(숨은 테스트, 정답 설명, 채점 체크리스트) |
| read_only | BOOLEAN | | | false | 응시자가 고칠 수 없는 파일(로그, 자료)이면 true. 편집기에 READ ONLY 표시 |

### document_pages (문서 페이지 텍스트)
PDF에서 뽑은 글자를 페이지별로 저장한다. **응시용 AI 어시스턴트**는 이 테이블을 검색하지 않고, 응시자가 고른 페이지(예: "B.pdf 3~5쪽")의 글자만 꺼내 보낸다. 그래서 "여러 문서에서 필요한 부분을 찾는 능력"이 그대로 평가된다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| task_file_id | BIGINT | PK, FK → task_files | | | 어느 PDF의 페이지인지 |
| page_no | INTEGER | PK | | | 페이지 번호(1부터). PDF와 함께 복합 PK |
| text | TEXT | | | | 그 페이지에서 뽑은 글자 |

### document_chunks (문서 조각, 채점용 RAG)
채점 모델이 응시자의 답과 관련된 문서 부분을 의미 검색으로 찾을 때 쓴다(응시용 AI는 쓰지 않는다). 벡터 DB를 따로 두지 않고 같은 PostgreSQL에 pgvector 확장으로 저장해서, 다른 테이블과 실제 외래 키로 연결된다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| chunk_id | BIGSERIAL | PK | | 자동 증가 | 조각 번호 |
| task_file_id | BIGINT | FK → document_pages(task_file_id, page_no), UQ | | | 어느 PDF의 조각인지 |
| page_no | INTEGER | FK → document_pages(task_file_id, page_no), UQ | | | 어느 페이지의 조각인지. 조각은 페이지 경계를 넘지 않게 자른다. 문항 근거 페이지(question_sources.pages)와 비교할 때 쓴다 |
| chunk_no | INTEGER | UQ(task_file_id, page_no, chunk_no) | | | 페이지 안 조각 순서 |
| content | TEXT | | | | 조각 글자. 검색 결과로 채점 모델에 넘긴다. 페이지 글자의 일부라 **의도된 중복(반정규화)**이다. 임베딩과 함께 다시 만드는 파생 데이터라 검색할 때마다 잘라 내지 않도록 함께 둔다 |
| token_count | INTEGER | | | | 조각의 토큰 수. 채점 모델에 넘길 양을 계산할 때 쓴다 |
| embedding | VECTOR(1536) | 인덱스(HNSW, 코사인) | | | 조각의 임베딩 벡터. 1536은 OpenAI 계열 임베딩 기준이고, 임베딩 모델을 확정하면 차원을 맞춘다 |

쓰임: 문항 채점(question_results)에서 응시자 답과 관련된 조각을 찾아 정답 근거 페이지와 대조, 통제력 판정(C2, 자료와 다른 수치)에서 관련 조각만 채점 모델에 넘겨 토큰을 줄인다.

### task_questions (문항)
객관식, 주관식 문항과 제출 후 후속 질문을 한 테이블에 둔다. 문항을 고칠 때는 수정하지 않고 새 행을 추가한다(예전 답변이 바뀐 질문에 붙지 않게).

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| question_id | BIGSERIAL | PK | | 자동 증가 | 문항 번호 |
| task_id | BIGINT | FK → tasks | | | 어느 과제의 문항인지 |
| stage | VARCHAR(10) | | | | 언제 묻는지. `TASK` 과제 푸는 중, `FOLLOWUP` 제출 후 후속 질문 |
| question_type | VARCHAR(10) | | | | 답하는 방식. `SINGLE` 객관식 하나, `MULTI` 객관식 여러 개, `SHORT` 단답형, `ESSAY` 서술형 |
| seq | INTEGER | | | | 문항 순서. 화면에 1/3, 2/3으로 보인다 |
| content | TEXT | | | | 문제 내용 |
| points | INTEGER | | O | | 배점. 후속 질문은 점수 문항이 아니라 비워 둔다 |
| answer_guide | TEXT | | O | | 서술형 채점 기준. LLM 채점 모델에 넘긴다. 응시자에게는 보이지 않는다 |
| active | BOOLEAN | | | true | 지금 쓰는 문항인지. 문항을 고치면 옛 행은 false, 새 행은 true |

`UNIQUE (question_id, question_type)`: question_id만으로도 유일하지만, 답변 테이블이 (문항 ID, 유형) 쌍을 외래 키로 가리킬 수 있게 둔다.

### question_choices (객관식 보기)

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| choice_id | BIGSERIAL | PK | | 자동 증가 | 보기 번호 |
| question_id | BIGINT | FK → task_questions | | | 어느 문항의 보기인지 |
| seq | INTEGER | | | | 보기 순서(①②③④) |
| content | TEXT | | | | 보기 내용 |

### short_answer_keys (단답형 정답)
단답형 정답을 여러 표현으로 인정하기 위한 목록. 코드가 응시자의 답과 비교해 채점한다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| answer_key_id | BIGSERIAL | PK | | 자동 증가 | 답안 번호. 인정 답안 하나를 고치거나 지울 때 이 번호로 가리킨다 |
| question_id | BIGINT | FK → task_questions, UQ(question_id, accepted) | | | 어느 문항의 정답인지 |
| accepted | VARCHAR(200) | UQ(question_id, accepted) | | | 인정하는 답. 예: "잠식 효과", "카니발라이제이션". 문항과 함께 UNIQUE라 같은 답이 두 번 들어가지 않는다 |

PK를 대리키(답안 ID)로 두고, 원래 복합 PK였던 (문항, 인정 답안)은 UNIQUE로 남겨 같은 답이 두 번 들어가는 것을 계속 막는다.

### question_sources (문항 근거 문서)
문항 ↔ PDF의 다대다 관계 테이블. 문항마다 정답 근거가 어느 문서 어느 페이지에 있는지 적는다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| question_id | BIGINT | PK, FK → task_questions | | | 문항 |
| task_file_id | BIGINT | PK, FK → task_files | | | 근거가 있는 문서 |
| pages | VARCHAR(50) | | O | | 근거 페이지. 예: "3, 7-8" |
| note | TEXT | | O | | 출제 메모(이 문서에서 무엇을 찾아야 하는지). 응시자에게는 보이지 않는다 |

쓰임: "문항마다 PDF 2개 이상 참조" 출제 규칙 검사, 응시자가 실제로 첨부한 문서와 비교해 "필요한 문서를 찾았나" 자동 측정, 서술형 채점과 해설.

## 2. 응시

### attempts (응시)
응시 1회. 대화, 파일, 기록, 답변, 채점이 모두 여기에 매달린다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |

| user_id | BIGINT | FK → users | | | 누가 응시했는지 |
| task_id | BIGINT | FK → tasks | | | 어떤 과제를 풀었는지. 같은 사람이 같은 과제를 여러 번 풀 수 있어 (user_id, task_id)에 UQ를 걸지 않는다 |
| mode | VARCHAR(10) | | | | `SELF` 자가진단, `LIVE` 실전 시험(회차로 입장, 감독, 제출 후 이동 화면이 다름). LIVE 응시는 exam_participants가 이 응시를 가리킨다 |
| status | VARCHAR(20) | | | | 진행 상태. `SOLVING` 응시 중 → `FOLLOWUP` 후속 질문 중 → `SCORING` 채점 중 → `DONE` 완료, 실패 시 `FAILED`. 내 기록 화면의 상태 표시 |

| started_at | TIMESTAMPTZ | | | now() | 시작 시각. 소요 시간, 첫 유효 결과 시간(D5) 계산의 기준 |

### attempt_files (응시 작업 파일)

| path | VARCHAR(255) | UQ(attempt_id, path) | | | 파일 경로. 한 응시 안에서 같은 경로는 하나 |
| content | TEXT | | | | 지금 내용. 저장할 때마다 이 값을 고친다. 제출 시점의 값이 채점 대상 |
| updated_at | TIMESTAMPTZ | | | now() | 마지막 저장 시각 |

### chat_turns (AI 대화)
질문과 답 한 마디씩. 채점 근거 `#T03`의 그 번호가 turn_no다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| turn_id | BIGSERIAL | PK | | 자동 증가 | DB 안에서 쓰는 대화 번호 |
| attempt_id | BIGINT | FK → attempts, UQ(attempt_id, turn_no) | | | 어느 응시의 대화인지 |
| turn_no | INTEGER | UQ(attempt_id, turn_no) | | | 응시 안에서 1부터 매기는 턴 번호. 리포트의 `#T03` |
| role | VARCHAR(10) | | | | `USER` 응시자 질문, `AI` 어시스턴트 답 |
| content | TEXT | | | | 질문이나 답의 글 |

| task_file_id | BIGINT | FK → task_files | O | | 과제 자료를 첨부했을 때 원본 파일. `TASK_FILE`이면 반드시 있어야 한다(CHECK 제약) |

### attempt_events (작업 기록)
저장, 빌드, 실행, AI 수정 제안 적용 같은 행동 기록. 결과물만이 아니라 과정을 채점하는 근거다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| event_id | BIGSERIAL | PK | | 자동 증가 | 기록 번호 |
| attempt_id | BIGINT | FK → attempts | | | 어느 응시의 기록인지 |
| type | VARCHAR(20) | | | | 종류. `SAVE` 저장, `BUILD` 빌드, `RUN` 실행, `AI_EDIT` 수정 제안 적용/거절, `SUBMIT` 제출 등 |
| payload | JSONB | | O | | 종류마다 다른 상세. 예: SAVE `{"path":"src/…","length":1436}`, RUN `{"compiled":true,"passed":3,"failed":0}`, AI_EDIT `{"turn":8,"action":"reject"}` |
| created_at | TIMESTAMPTZ | | | now() | 일어난 시각 |

쓰임: 실행 결과로 검증 여부(C1), 실패 뒤 같은 시도 반복(P3), 첫 유효 결과 시간(D5), 저장 글자 수로 반복 작업을 직접 했는지(J3)를 판정한다.

답변은 답하는 방식에 따라 두 테이블로 나눈다. 객관식은 "고른 보기"가, 단답형·서술형은 "글 하나"가 답이라 저장할 것이 다르기 때문이다. 어느 테이블에 들어갈지는 문항 유형이 정하고, 두 테이블 모두 `(question_id, question_type)` 복합 외래 키로 task_questions를 가리켜서 **문항의 실제 유형과 다른 테이블에는 답이 들어가지 못한다**(예: 객관식 문항에 글 답변, 단답형 문항에 보기 선택).

### choice_answers (객관식 답변)
응시 ↔ 보기의 다대다 관계 테이블. 고른 보기 하나가 한 행이다. 복수 선택(MULTI)은 고른 만큼 행이 생긴다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| attempt_id | BIGINT | PK, FK → attempts | | | 어느 응시의 답인지 |
| question_id | BIGINT | FK → task_questions(question_id, question_type), FK → question_choices(choice_id, question_id) | | | 어느 문항인지. 보기가 이 문항의 보기인지도 외래 키로 확인한다 |
| question_type | VARCHAR(10) | FK → task_questions(question_id, question_type) | | | `SINGLE` 하나 고르기, `MULTI` 여러 개 고르기(CHECK). 문항의 실제 유형과 같아야만 들어간다 |
| choice_id | BIGINT | PK, FK → question_choices | | | 고른 보기. 응시와 함께 복합 PK라 같은 보기를 두 번 고를 수 없다 |
| answered_at | TIMESTAMPTZ | | | now() | 고른 시각 |

`SINGLE` 문항은 부분 유니크 인덱스(`uq_choice_answers_single`: question_type = 'SINGLE'인 행에서 (attempt_id, question_id) 유일)로 한 응시에 보기를 하나만 고를 수 있다. 보기를 바꾸면 행을 지우고 새로 넣는다.

### text_answers (단답형·서술형 답변)
글로 쓰는 답. 단답형, 서술형, 제출 후 후속 질문이 여기에 들어간다. 단답형과 서술형은 저장하는 것(글 하나)이 같아서 한 테이블로 둔다. 채점 방식(단답형은 코드 비교, 서술형은 LLM)은 question_results.method로 구분한다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| text_answer_id | BIGSERIAL | PK | | 자동 증가 | 글 답변 번호 |
| attempt_id | BIGINT | FK → attempts, UQ(attempt_id, question_id) | | | 어느 응시의 답인지 |
| question_id | BIGINT | FK → task_questions(question_id, question_type), UQ(attempt_id, question_id) | | | 어느 문항인지. 한 응시에서 같은 문항에 답은 하나 |
| question_type | VARCHAR(10) | FK → task_questions(question_id, question_type) | | | `SHORT` 단답형, `ESSAY` 서술형(CHECK). 문항의 실제 유형과 같아야만 들어간다 |
| content | TEXT | | | | 답변 글. 비어 있으면 안 된다(무응답은 서비스가 정한 표시로 저장) |
| answered_at | TIMESTAMPTZ | | | now() | 답한 시각 |

**question_type을 답변에도 두는 이유:** 문항 테이블에 이미 있는 값이라 중복이지만, 복합 외래 키로 문항과 묶여 있어 다른 값은 들어갈 수 없다(정합성이 보장되는 반정규화). 이 컬럼 덕분에 "유형에 맞는 테이블에만 답이 들어간다"를 DB가 직접 지킨다.

**DB로 못 막는 것(서비스 코드에서 지킴):** 한 문항에 객관식 답변과 글 답변이 둘 다 생기는 것은 유형 외래 키 때문에 실제로는 생길 수 없지만, "객관식 문항인데 보기를 하나도 안 고름(미응답)"은 행이 없는 상태라 DB가 알 수 없다. 제출할 때 서비스가 검사한다.

## 5. 채점 결과

### scorings (채점)
채점 1회 = 리포트 1개. 같은 응시를 기준이 바뀔 때 다시 채점할 수 있어 응시와 1:N이다. 실제 응시 채점만 저장한다(채점 툴 실험 기록은 git의 grader/runs 파일).

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| scoring_id | BIGSERIAL | PK | | 자동 증가 | 채점 번호 |
| attempt_id | BIGINT | FK → attempts | | | 어느 응시를 채점했는지 |
| version_id | BIGINT | FK → prompt_versions | | | 어느 기준(버전)으로 채점했는지. 결과를 해석하는 핵심 정보 |
| status | VARCHAR(20) | | | | `RUNNING` 채점 중, `DONE` 완료, `FAILED` 실패 |
| error | TEXT | | O | | 실패했을 때 오류 내용 |
| started_at | TIMESTAMPTZ | | | now() | 채점 시작 시각 |
| finished_at | TIMESTAMPTZ | | O | | 채점 끝난 시각 |

총점과 항목 점수는 저장하지 않고 check_results의 감점으로 계산한다(배점 − 감점 합). 조회가 잦으면 반정규화 1순위 후보.

| input_tokens | INTEGER | | | 0 | 입력 토큰. 토큰은 체크마다가 아니라 호출마다 생겨서 여기에 둔다 |
| output_tokens | INTEGER | | | 0 | 출력 토큰 |
| cached_tokens | INTEGER | | | 0 | 입력 중 프롬프트 캐시로 싸게 처리된 토큰. 비용 계산 |

### question_results (문항 채점 결과)

|---|---|---|---|---|---|

| question_id | BIGINT | PK, FK → task_questions | | | 어느 문항인지 |
| score | INTEGER | | | | 얻은 점수 |
| method | VARCHAR(10) | | | | `AUTO` 객관식·단답형을 코드로 채점, `JUDGE` 서술형을 LLM이 채점 |
| reason | TEXT | | O | | 서술형 판정 이유 |

## 6. 실전 시험 · 감독

실전 응시(attempts.mode = `LIVE`)에서만 쓴다. 자가진단(`SELF`)은 회차와 감독 없이 응시한다.
감독 영상은 서버로 보내지 않는다. 브라우저에서 분석하고, 이상이 생긴 순간의 이벤트와 스냅샷 1장만 저장한다. 얼굴로 사람을 식별하지 않으므로(얼굴이 있는지, 몇 개인지만 봄) 생체인식정보를 저장하지 않는다.

### exam_sessions (시험 회차)
기업 담당자가 여는 시험 한 번. 같은 회차의 응시자는 모두 같은 시각에 시작하고 끝난다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| session_id | BIGSERIAL | PK | | 자동 증가 | 회차 번호 |
| company_id | BIGINT | FK → companies | | | 회차를 연 회사. 이 회사 담당자만 회차와 결과를 볼 수 있다 |
| task_id | BIGINT | FK → tasks | | | 이 회차에서 푸는 과제 |
| title | VARCHAR(100) | | | | 회차 이름. 예: "2026 하반기 백엔드 신입 실전" |
| entry_code | VARCHAR(20) | UQ | | | 입장 코드. 응시자가 입장 화면에 입력한다. 예: `PAIR-7K2Q` |
| starts_at | TIMESTAMPTZ | | | | 시작 시각. 이 시각 전에는 입장해도 대기한다 |
| ends_at | TIMESTAMPTZ | | | | 종료 시각. 이 시각에 전원 자동 제출되고 채점 요청이 큐로 몰린다. `ends_at > starts_at` 검사 |
| proctoring | BOOLEAN | | | true | 감독(카메라, 브라우저 이벤트) 사용 여부. false면 동의·감독 없이 응시 |
| created_by | BIGINT | FK → users | | | 회차를 만든 기업 담당자(또는 관리자). 담당자라면 같은 회사 소속이어야 한다(서비스 코드에서 검사) |
| created_at | TIMESTAMPTZ | | | now() | 만든 시각 |

### exam_participants (회차 응시 대상자)
회차에 초대한 사람. 초대할 때는 회원이 아닐 수 있어서 이메일과 이름을 따로 둔다. 입장하면서 로그인(또는 가입)하면 회원과 응시가 연결된다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| participant_id | BIGSERIAL | PK | | 자동 증가 | 대상자 번호 |
| session_id | BIGINT | FK → exam_sessions, UQ(session_id, email) | | | 어느 회차의 대상자인지 |
| email | VARCHAR(255) | UQ(session_id, email) | | | 초대 메일 주소. 같은 회차에 같은 사람을 두 번 초대할 수 없다 |
| name | VARCHAR(50) | | | | 기업이 등록한 이름 |
| invite_token | VARCHAR(64) | UQ | | | 메일 입장 링크에 들어가는 개인별 토큰. 링크로 들어오면 입장 코드 없이 본인으로 인식 |
| user_id | BIGINT | FK → users | O | | 입장할 때 로그인한 회원. 입장 전에는 비어 있다 |
| attempt_id | BIGINT | FK → attempts, UQ | O | | 입장하면서 만든 응시. 응시 하나는 대상자 한 명에게만 연결된다. 입장 전에는 비어 있다 |
| invited_at | TIMESTAMPTZ | | | now() | 초대 시각 |
| entered_at | TIMESTAMPTZ | | O | | 입장 시각. 비어 있으면 미입장(관리자 화면의 "미응시") |

### proctor_consents (감독 동의 · 환경 점검)
응시 시작 전에 받는 카메라 사용 동의와 환경 점검 결과. 응시 하나에 한 번이라 attempt_id가 PK다(1:1).

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| attempt_id | BIGINT | PK, FK → attempts | | | 어느 응시의 동의인지 |
| consent_version | VARCHAR(20) | | | | 동의서 버전. 문구가 바뀌어도 누가 어느 문구에 동의했는지 남는다 |
| env_check | JSONB | | | | 환경 점검 결과. 예: `{"camera": true, "fullscreen": true, "browser": "Chrome 142"}` |
| consented_at | TIMESTAMPTZ | | | now() | 동의 시각 |

### proctor_events (감독 이벤트)
부정행위로 의심되는 순간 하나. 리포트의 "주의 구간"과 관리자 화면에 표시한다. 자동 탈락이 아니라 사람이 판단하도록 보여 주는 기록이다.

| 컬럼 | 타입 | 키 | NULL | 기본값 | 설명 |
|---|---|---|---|---|---|
| proctor_event_id | BIGSERIAL | PK | | 자동 증가 | 감독 이벤트 번호 |
| attempt_id | BIGINT | FK → attempts | | | 어느 응시에서 생긴 이벤트인지 |
| type | VARCHAR(20) | | | | 종류(CHECK). 브라우저: `TAB_HIDDEN` 탭 전환, `WINDOW_BLUR` 창 이탈, `PASTE` 외부 붙여넣기, `FULLSCREEN_EXIT` 전체화면 이탈. 카메라: `NO_FACE` 얼굴 없음, `MULTI_FACE` 여러 얼굴, `HEAD_TURN` 고개 돌림, `PHONE` 휴대폰 |
| started_at | TIMESTAMPTZ | | | | 시작 시각 |
| duration_ms | INTEGER | | | 0 | 지속 시간(ms). 붙여넣기처럼 순간인 이벤트는 0. 0 이상 검사 |
| confidence | NUMERIC(4,3) | | O | | 카메라 감지 모델의 확신도(0~1). 브라우저 이벤트는 확실하므로 비어 있다. 관리자 화면에서 낮은 확신도는 흐리게 보여 오탐을 줄인다 |
| detail | JSONB | | O | | 종류마다 다른 상세. 예: 붙여넣기 `{"chars": 840, "fromAssistant": false}`, 고개 돌림 `{"yawDeg": 48}` |
| snapshot_key | VARCHAR(255) | | O | | 그 순간의 카메라 스냅샷 저장 위치(파일 저장소 경로). 카메라 이벤트만 있다 |
| snapshot_deleted_at | TIMESTAMPTZ | | O | | 보관 기간이 지나 스냅샷을 지운 시각. 이벤트 기록은 남기고 사진만 지운다 |

**attempt_events(작업 기록)와 따로 둔 이유:** 작업 기록은 채점에 쓰는 응시자의 작업이고, 감독 이벤트는 채점과 무관한 부정행위 의심 기록이다. 보는 사람(채점 모델 / 기업 담당자)과 보관 기간(영구 / 스냅샷은 기간 후 삭제)이 달라서 분리했다. 붙여넣기는 채점에도 쓰일 수 있지만, 우리 어시스턴트 답에서 복사한 붙여넣기(`fromAssistant: true`)는 감독 이벤트로 남기지 않는다.

## 조회용 인덱스

PostgreSQL 은 외래 키에 인덱스를 자동으로 만들지 않는다. 화면에서 자주 따라가는 외래 키 10개에만 건다. UNIQUE 나 복합 PK 의 첫 컬럼인 외래 키(`chat_turns.attempt_id`, `check_results.scoring_id` 등)는 그 인덱스를 함께 쓰므로 따로 만들지 않는다. 나머지 외래 키는 데이터가 적은 기준 테이블 쪽이거나 거의 조회하지 않아 넣지 않았다.

| 인덱스 | 컬럼 | 쓰는 곳 |
|---|---|---|
| idx_attempts_user_id | attempts.user_id | 내 응시 목록 |
| idx_attempt_events_attempt_id | attempt_events.attempt_id | 응시 작업 기록 |
| idx_checkpoints_attempt_id | checkpoints.attempt_id | 복기 트리 |
| idx_chat_attachments_turn_id | chat_attachments.turn_id | 대화의 첨부 |
| idx_scorings_attempt_id | scorings.attempt_id | 리포트 |
| idx_judge_calls_scoring_id | judge_calls.scoring_id | 채점 토큰 집계 |
| idx_judge_verdicts_result_id | judge_verdicts.result_id | 리포트(체크별 모델 판정) |
| idx_exam_sessions_company_id | exam_sessions.company_id | 회사의 회차 목록(관리자 화면) |
| idx_exam_participants_user_id | exam_participants.user_id | 내 실전 시험 목록 |
| idx_proctor_events_attempt_id | proctor_events.attempt_id | 리포트 주의 구간, 관리자 감독 확인 |
| idx_document_chunks_embedding | document_chunks.embedding (HNSW, 코사인) | 채점용 의미 검색 |
