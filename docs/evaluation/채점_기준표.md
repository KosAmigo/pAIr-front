# pAIr 채점 기준표 (감점식, 총점 100점)

> 작성일: 2026-11-11, 2026-11-12 개정 (재현성 삭제, 문제 분해력·위임 판단력 추가. 근거: [새_평가기준_초안.md](새_평가기준_초안.md))
> 이 문서가 채점의 기준이다. 이전 문서 [재현성_AI결과도출력.md](재현성_AI결과도출력.md)의 하위 기준(R1~R3, D1~D5, 가중 평균 방식)은 이 문서로 대체한다.
> 구현: `backend/src/main/java/com/pair/scoring/Rubric.java`, `ScoringService.java`

## 1. 항목과 배점

프로그래머스 AI 역량평가 항목에서 AI 기초 이해력과 재현성을 빼고, 국내외 평가 조사에서 공통으로 보는 문제 분해력과 위임 판단력을 더해 6개 항목으로 구성한다.

| 항목 | 배점 | 무엇을 보나 |
|---|---|---|
| AI 활용력 | 20 | AI에게 목표와 맥락을 주고, 막히면 전략을 바꾸고, 지시가 혼자서 뜻이 통하는가 |
| AI 통제력 | 15 | AI 결과를 검증하고, 틀리거나 위험한 제안을 걸러내는가 |
| 문제 분해력 | 10 | 문제를 확인 가능한 크기로 나누고, 순서대로 요청하는가 |
| 위임 판단력 | 10 | AI에게 맡길 일과 직접 판단할 일을 가려내는가 |
| AI 결과 도출력 | 30 | 요구사항을 충족하는 결과물을 시간 안에 만들어 냈는가 |
| 성과 잠재력 | 15 | 결과를 자기 말로 설명하고, 한계와 다음 개선을 아는가 |
| **합계** | **100** | |

- 재현성을 뺀 이유: 같은 응시를 다시 채점하면 R1(다시 실행)이 0~8점으로 흔들려 응시자 능력보다 모델의 무작위성을 재는 면이 컸고, 다른 평가 서비스에서는 따로 재지 않는다. R2(지시가 혼자서 뜻이 통하는지)는 활용력 U7로 옮겼고, R1과 R3은 버렸다. 다시 실행이 없어져 채점 비용과 시간도 줄었다.

## 2. 채점 방식

- 각 항목은 **배점에서 시작해 체크 항목에 걸릴 때마다 감점**한다. 항목 점수는 0점 아래로 내려가지 않는다.
- 총점은 6개 항목 점수의 합이다.
- 체크 판정 방식은 두 가지다.
  - **자동**: 시스템이 기록(테스트 결과, 이벤트, 다시 실행 결과)으로 판정한다.
  - **판정**: 채점 모델이 대화 기록, 최종 파일, 후속 답변을 보고 "걸림 / 안 걸림"을 판정한다. 걸렸다고 할 때는 근거(대화 턴 `#T03`이나 파일 이름)를 반드시 대야 하고, 근거가 없으면 감점하지 않는다.
- **이중 채점**: 판정 체크는 서로 다른 회사 모델 두 개가 따로 판정한다.
  - 두 모델의 감점을 **평균**한다(소수점 버림). 모델마다 근거를 대고 "걸림"이면 배점만큼, 아니면 0점으로 보고 평균한다. 1개당 감점(비개발 D1)은 모델마다 센 개수로 계산해 평균한다.
  - 둘 다 "걸림"이면 감점, 한쪽만 "걸림"이면 **판정 엇갈림**으로 표시하고 절반만 감점한다(예: 5점 → 2점). 리포트에 두 모델의 판정과 이유가 함께 보인다. 판정 엇갈림이 잦은 체크 항목은 판정 기준 문장을 고칠 후보다.
  - 예전에는 둘 다 "걸림"일 때만 감점했는데, 가상 응시 검증에서 너무 관대하게 나와(통째로 맡긴 응시가 62점) 평균으로 바꿨다.
  - 한 모델 호출이 실패하면 남은 모델 하나로 판정하고, 리포트 메모에 남긴다.
  - 한 모델이 잘못 감점하는 일을 다른 모델이 막아 주므로, 비싼 모델 하나보다 싼 모델 두 개가 감점 오류가 적다.

| 용도 | 모델 | 추론 강도 | 가격 ($/1M 입력/출력) |
|---|---|---|---|
| 판정 1 | Claude Haiku 5.5 (`claude-haiku-5-5`) | medium | 0.10 / 0.50 |
| 판정 2 | OpenAI gpt-6.1-terra | medium | 1 / 5 |

  - 모델과 추론 강도는 `backend/src/main/resources/application.yml`의 `pair.judge`에서 바꾼다. 더 정확하게 보려면 Claude 쪽을 `claude-sonnet-5-5`(2 / 10)로 올린다.
  - 프롬프트는 응시와 관계없이 같은 앞부분(채점 규칙, 과제, 숨은 정답, 체크 항목)을 먼저 두고 프롬프트 캐시로 재사용한다.
- **시스템 오류는 응시자 책임으로 보지 않는다.** AI 답변이 비어 있던 턴(추론 모델이 출력 한도 안에서 답을 끝내지 못한 경우)과, 그 때문에 응시자가 다시 묻거나 재촉한 질문은 감점 근거로 쓰지 않는다. 2026-11-11부터는 빈 답을 저장하지 않고 응시자에게 다시 보내 달라고 안내한다.
- **AI 수정 제안**: 어시스턴트는 파일 수정을 제안할 수 있고(답변 속 수정 블록), 응시자가 [적용]하면 파일에 반영되고 [거절]하면 반영되지 않는다. 적용과 거절은 이벤트로 남고 채점 모델에 "#T04 수정 제안 적용 src/..."처럼 전달된다. 적용한 제안은 응시자가 결과물에 넣은 것으로(C1: 적용 뒤 테스트나 확인 없이 제출하면 걸림), 거절한 제안은 채택하지 않은 제안으로(P2) 본다. 어시스턴트는 여전히 대화창에 붙여 넣은 내용만 보며, 파일 목록(이름)만 안다.
- 한 가지 행동을 두 항목에서 겹쳐 감점하지 않도록 체크 항목을 나눴다. 예: "AI 오답이 최종본에 남음"은 통제력(C2)에서만 감점하고, 도출력은 숨은 테스트와 체크리스트로만 본다.
- `개발`, `비개발` 표시는 해당 과제 유형에만 적용한다. 표시가 없으면 공통이다.

### 채점 프롬프트 버전과 채점 툴 (2026-11-12)

- 공통 채점 규칙과 체크별 판정 기준은 코드가 아니라 **프롬프트 버전 파일**(`grader/versions/*.json`)에서 읽는다. 배점은 아래 감점표로 고정이고 버전에서 바꿀 수 없다. 아래 판정 기준 문장은 기본 버전 `v2_기본`(6개 역량)의 값이다. `v1_기본`은 예전 5개 항목 기준이다.
- 실제 응시 채점은 채점 툴에서 [실제 채점에 사용]으로 지정한 버전을 쓴다(각자 PC 설정, 기본은 `v2_기본`). 리포트의 `promptVersion`에 어느 버전으로 채점했는지 남는다.
- 채점 툴(메인 화면 오른쪽 위 아이콘)에서 버전을 새로 만들고, 샘플 응시(`grader/samples/`)나 내 응시를 골라 N번씩 실험 채점해 점수 분포, 체크별 흔들림, 버전 차이를 본다. 실험 결과는 응시자 리포트와 따로 저장한다.
- 실험 채점은 같은 응시를 N번 반복 채점해 점수 분포를 본다. 채점 설정(채점 모델 1번씩)은 실제 채점과 같다. 실제 채점에서 몇 번 평균을 낼지는 반복 채점 결과를 보고 팀이 정한다.
- 채점은 4건씩 동시에 돌리고, 두 채점 모델을 동시에 부른다.
- 실험 채점은 **배치 API**로도 할 수 있다(비용 50%, 결과는 몇 분~최대 24시간 뒤). 요청 내용은 일반 채점과 같고, 두 채점 모델의 판정을 한 번에 보낸다. Spring AI(1.1, 2.x 모두)에 배치 기능이 없어 이 부분만 Spring RestClient로 직접 부른다. 배치 ID와 받은 결과는 실험 기록에 저장해서 서버를 껐다 켜도 이어서 받는다. 단계마다 최대 대기 시간(기본 10분, 채점 툴에서 설정)을 넘기면 안 끝난 배치는 취소하고, 결과가 없는 요청만 일반 API(정가)로 바로 채점한다. 실제 응시 채점은 늘 일반 API다.
- 후속 질문 문구는 응시자가 답할 때의 문구를 응시 기록(`followUpQuestions`)에 함께 저장하고, 채점은 그 문구로 한다. 과제의 후속 질문을 나중에 바꿔도 예전 응시의 답이 엉뚱한 질문에 붙지 않는다.

## 3. 감점표

### AI 활용력 (20점)

| 코드 | 체크 항목 | 감점 | 판정 |
|---|---|---|---|
| U0 | AI에게 한 번도 질문하지 않음 (이 항목 0점) | -20 | 자동 |
| U1 | 첫 질문에서 무엇을 하려는지(목표)를 밝히지 않음 | -4 | 판정 |
| U2 | 필요한 코드, 로그, 자료를 붙이지 않아 AI가 추측해서 답하게 함 | -5 | 판정 |
| U3 | 대부분의 질문에서 원하는 출력 형식이나 범위를 정하지 않음 | -3 | 판정 |
| U5 | 막혔을 때 거의 같은 질문을 3번 이상 반복하고 전략을 바꾸지 않음 | -3 | 판정 |
| U6 | AI 답변을 받은 뒤 이어서 확인하거나 좁혀 묻는 질문이 없음 | -3 | 판정 |
| U7 | 핵심 지시가 앞 대화 없이는 뜻이 통하지 않음 ("그거 다시 해줘" 등, 예전 재현성 R2) | -2 | 판정 |

- U4(통째로 맡김)는 문제 분해력 K1로 옮겼다. 코드 번호는 예전 기록과 헷갈리지 않게 비워 둔다.

### AI 통제력 (15점)

| 코드 | 체크 항목 | 감점 | 판정 |
|---|---|---|---|
| C0 | AI를 쓰지 않아 AI 결과를 검증하고 통제하는 모습을 볼 수 없음 (이 항목 0점) | -15 | 자동 |
| C1 | AI가 준 코드나 수치를 실행, 테스트, 자료 대조 없이 최종본에 넣음 | -5 | 판정 |
| C2 | AI의 오답이나 근거 없는 수치가 최종본에 남음 | -5 | 판정 |
| C3 | 증상만 가리는 제안(타임아웃 늘리기, 전체 잠금 등)이나 근거 없는 주장을 따져 보지 않고 받아들임 | -3 | 판정 |
| C4 | AI 답변의 근거나 이유를 한 번도 확인하지 않음 | -2 | 판정 |

### 문제 분해력 (10점)

| 코드 | 체크 항목 | 감점 | 판정 |
|---|---|---|---|
| K0 | AI를 쓰지 않아 AI에게 일을 나눠 맡기는 모습을 볼 수 없음 (이 항목 0점) | -10 | 자동 |
| K1 | 너무 큰 덩어리: 단계 없이 한 덩어리로 맡겨 중간 결과를 확인하지 못함 (앞 결과에 기대는 단계를 한 요청에 묶음, 또는 "이 코드 고쳐줘"처럼 최종 결과만 바로 요청하고 이후에도 나눠 진행하지 않음) | -5 | 판정 |
| K2 | 순서 거꾸로: 앞 단계가 끝나기 전에 뒤 단계를 요청함 (원인 확인 전에 수정, 자료 확인 전에 결론, 실패하기 전에 "알아서 해결") | -3 | 판정 |
| K3 | 너무 잘게 쪼갬: 한 번에 해도 되는 단순한 일을 여러 턴으로 나눠 턴만 늘림 | -2 | 판정 |

- 세 체크는 서로 다른 축을 본다. K1과 K3은 한 번에 맡기는 크기의 양 끝이라 한 응시가 둘 다 걸리기 어렵고, K2는 크기와 관계없이 순서만 본다.
- 서로 관계없는 간단한 일을 함께 요청한 것(예: "오타 고치고 제목도 바꿔 줘")은 K1에 걸리지 않는다.
- K1은 대화 전체를 본다. 첫 질문이 결과 요청이어도 이후 원인 확인, 수정, 검증으로 나눠 진행했으면 걸리지 않는다.
- 2026-11-13 실험: 처음 K1 문구(여러 단계를 한 요청에 묶음)는 "이 코드 고쳐줘" 한 줄로 통째로 맡긴 샘플을 잡지 못했다(0/3). "최종 결과만 바로 요청" 경우를 더한 뒤 3/3으로 잡았고, 모범 응시는 한 번도 걸리지 않았다(샘플 7건 × 3회).

### 위임 판단력 (10점)

| 코드 | 체크 항목 | 감점 | 판정 |
|---|---|---|---|
| J0 | AI를 쓰지 않아 위임 판단을 볼 수 없음 (이 항목 0점) | -10 | 자동 |
| J1 | 과제의 핵심 판단(근본 원인 결정, 최종 결론과 추천안)을 AI에게 맡기고 자기 판단 없이 그대로 씀 | -4 | 판정 |
| J2 | 주어진 파일을 열어 보면 바로 아는 내용이나 단순 계산을 AI에게 여러 번 물음 | -3 | 판정 |
| J3 | AI에게 맡기기 좋은 반복 작업을 직접 하느라 시간을 많이 씀 | -3 | 판정 |

- J1과 통제력 C1, C3의 구분: C1, C3는 "AI 답을 검증했는가", J1은 "판단 자체를 누가 내렸는가"를 본다.
- J3 판정을 위해 채점 모델에 주는 이벤트 요약에 파일 저장마다 글자 수를 넣는다. 근거가 분명하지 않으면 걸리지 않음으로 판정한다. 파일럿에서 판정이 흔들리면 빼는 후보다.
- AI를 쓰지 않은 응시는 활용력(U0), 통제력(C0), 문제 분해력(K0), 위임 판단력(J0)이 모두 0점이고 이 네 항목의 다른 체크는 판정하지 않는다. 결과 도출력과 성과 잠재력만 받을 수 있어 최대 45점이다.

### AI 결과 도출력 (30점)

| 코드 | 체크 항목 | 감점 | 판정 |
|---|---|---|---|
| D0 | 제출 코드가 컴파일되지 않음 (이 항목 0점) `개발` | -30 | 자동 |
| D1 | 숨은 필수 테스트 실패 1개당 (4개) `개발` | 1개당 -5 | 자동 |
| D1 | 필수 체크리스트 미충족 1개당 (결론, 근거 3개, 잠식 효과, 리스크와 대응, 수치 정확성 중 앞 4개) `비개발` | 1개당 -5 | 판정 |
| D2 | 엣지 케이스 누락: 숨은 선택 테스트 실패 `개발` / 의향을 실제 전환율로 보정하지 않음 `비개발` | -2 | 자동 / 판정 |
| D3 | 수정을 확인하는 테스트를 추가하지 않음 `개발` / 근거 수치에 출처(어느 자료인지)를 밝히지 않음 `비개발` | -3 | 자동 / 판정 |
| D4 | NOTES.md의 원인 설명이 비어 있거나 핵심 원인(잠금 순서 불일치로 인한 교착)과 맞지 않음 `개발` (-3) / 결론과 근거가 서로 맞지 않음 `비개발` (-2) | -3 / -2 | 판정 |
| D5 | 첫 유효 결과가 30분을 넘김 (-2) / 끝까지 도달하지 못함 (-4) | 최대 -4 | 자동 |

- 첫 유효 결과: 개발은 "src 코드를 고친 뒤 테스트가 전부 통과한 첫 실행"(테스트 추가 여부와 무관, 테스트 추가는 D3에서만 감점), 비개발은 "필수 제목(결론, 근거, 리스크)을 모두 채운 첫 저장".
- 개발 과제 D4 판정에는 숨은 정답 설명(`tasks/order-deadlock/hidden/answer.md`)을 채점 모델에 함께 준다. 코드가 맞게 고쳐졌는지와 별개로, 응시자가 원인을 이해하고 설명했는지를 본다.
- 비개발의 "수치 정확성"(체크리스트 5번)은 통제력 C2에서 본다.

## 4. 리포트에 보이는 것

- 총점 `NN / 100`과 항목별 `점수 / 배점`
- 항목마다 체크 항목 표: 걸린 항목은 감점과 근거(대화 턴 링크)와 한 줄 이유, 안 걸린 항목은 "통과", 두 채점 모델이 엇갈린 항목은 "판정 엇갈림"과 모델별 판정
- 숨은 테스트 결과(개발), 토큰 사용량

## 5. 이전 방식과 달라진 점

| | 이전 | 지금 |
|---|---|---|
| 항목 | 재현성, AI 결과 도출력 2개만 채점 (6개 체계) | 6개 항목 모두 채점, 총점 100 |
| 점수 계산 | 하위 기준마다 0~100점을 매겨 가중 평균 | 배점에서 체크 항목별 감점 |
| 채점 모델 역할 | 하위 기준 점수(0~100)를 직접 매김 | 체크 항목이 "걸림 / 안 걸림"인지 근거와 함께 판정 |

감점식으로 바꾸면 채점 모델이 숫자를 고르지 않고 예/아니오만 판정하므로, 같은 응시를 다시 채점했을 때 점수가 덜 흔들리고 사람이 결과를 검토하기도 쉽다.

## 6. 남은 일
- 활용력, 통제력, 성과 잠재력 체크 항목은 초안이다. 각 담당자가 검토한다.
- 감점 크기는 파일럿 응시 결과를 보고 한 번 조정한다.
- 파일럿 채점 시트(Google 스프레드시트)는 아직 이전 방식(R1~R3, D1~D5)이다. 감점표에 맞춰 다시 만들어야 한다.
