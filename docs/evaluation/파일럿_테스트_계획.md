## 1. 목적

평가 기준을 실제 응시 기록에 적용해 보고, 아래 네 가지를 확인한다.

1. **기준이 명확한가:** 채점자 두 명이 같은 응시를 보고 비슷한 점수를 주는가
2. **자동 채점을 믿을 수 있는가:** LLM 채점이 사람 채점과 비슷한가
3. **변별력이 있는가:** 일부러 만든 나쁜 응시가 실제로 낮은 점수를 받는가
4. **운영할 수 있는 비용인가:** 출력 안정성(R2) 다시 실행에 응시 1건당 얼마가 드는가

통과하지 못한 기준만 고치고, 가중치는 결과를 보고 한 번만 조정한다. 그다음 20건으로 늘린다.

### 사람 채점은 왜 하나

운영 채점은 자동화한다. 사람 채점은 운영용이 아니라, **자동 채점이 맞는지 확인할 기준 답안을 만드는 용도**다.

- **LLM 점수가 일관돼도 맞다는 보장은 없다.** 매번 같은 방향으로 틀릴 수 있다. 맞는지 확인하려면 비교할 기준 답안이 필요하다.
- **사람을 두 명 두는 이유:** LLM과 사람 점수가 다를 때, LLM이 틀렸는지 기준 문구가 애매한지 구분하기 위해서다. A와 B가 서로 일치하는데 LLM만 벗어나면 LLM 쪽 문제다. A와 B부터 갈리면 기준 문구를 먼저 고친다.
- **설명 책임:** 기업 채용에 쓰는 평가이므로, 점수 근거를 물으면 "사람 채점과 일치를 확인한 자동 채점"이라고 답할 수 있어야 한다.
- **사람이 보는 범위는 좁다.** R2(다시 실행), D4(시간), 개발 과제의 D1(숨은 테스트)은 자동으로 잰다. 사람이 판단하는 기준은 R1, R3, D2, D3, D5와 비개발 과제의 D1뿐이다.

파일럿에서 만든 사람 채점 데이터는 버리지 않고 **기준 답안 세트**로 보관한다. 이후 모델이나 루브릭을 바꿀 때마다 다시 쓴다(§9).

## 3. 단계별 진행

### 0단계: 시험 재료 준비 (1~2일)
- 과제 2개의 설명, 제공 자료, 요구사항을 확정한다.
- **개발 과제:** 숨은 테스트를 작성한다. 필수 테스트와 선택 테스트를 구분한다. D1과 R2에 쓴다.
- **비개발 과제:** 필수 항목 체크리스트를 만든다(예: 결론, 근거 3개, 리스크 1개, 수치 출처). D1과 R2에 쓴다.
- 후속 질문 3문항을 과제별로 정한다. 기준 문서 §4 문항 뱅크에서 고른다.

**산출물:** 과제 문서 2개, 숨은 테스트 코드, 비개발 체크리스트, 후속 질문

### 1단계: 손 채점 예비 점검 (2~3일)
- 팀원이 웹 채팅으로 과제를 빠르게 풀어 대화 기록 5건을 만든다. 이 단계는 기준의 애매한 곳을 찾는 게 목적이라 기록 형식은 상관없다.
- 채점자 A, B가 서로 상의하지 않고 채점 시트로 채점한다. 점수마다 근거 턴 번호를 적는다.
- 점수 차이가 20점 이상 나는 기준은 둘이 모여 이유를 적는다. 그 이유를 바탕으로 기준표의 "점수 기준" 문구를 고친다.

**산출물:** 고친 점수 기준 문구, 애매했던 기준 목록

> 이 5건은 본 파일럿 10건과 별개다. 기준을 고친 뒤에는 쓰지 않는다.

### 2단계: 응시 기록 모으기 (3~4일)
- 웹 채팅 대신 **기록용 채팅 스크립트**로 풀게 한다. 웹 화면은 회사, 모델, 요청 설정, 토큰이 남지 않아 R2를 다시 실행할 수 없다.
- 스크립트가 턴마다 남길 것: 프롬프트, 응답, 회사, 모델, 요청 설정 원문, 토큰 사용량, 시각
- 응시자가 남길 것: 최종 제출물, 후속 질문 답변
- 진행자가 남길 것: 첫 유효 결과까지 걸린 시간(분), 대화 턴 수. 시트의 `응시목록` 탭에 입력한다.

**산출물:** 응시 10건의 대화 로그(JSON), 제출물, 후속 질문 답변

### 3단계: 채점 (3일)
- **사람 채점:** A와 B가 각자 `채점_A`, `채점_B` 탭에 입력한다. 상대 점수는 보지 않는다. 개발 과제의 D1은 숨은 테스트 결과를 기준표대로 옮겨 적기만 한다.
- **LLM 채점:** 기준별 루브릭 프롬프트로 채점하고 `채점_LLM` 탭에 옮긴다. 근거 턴 인용이 없는 점수는 무효로 처리한다.
- **자동 측정:**
  - R2: 기준 문서 §3 "R2 다시 실행 방식"대로 핵심 턴만 다시 실행한다. 2회 실행하고, 결과가 다르면 최대 5회까지 늘린다. 결과는 `R2_실측` 탭에 입력한다.
  - D4: `응시목록`의 시간 입력으로 자동 계산된다.
- 파일럿에서는 결과를 빨리 봐야 하므로 **일반 API**로 실행한다. 토큰 사용량은 전부 기록한다.
- R2 지표가 얼마나 흔들리는지 보려고, 같은 응시를 한 번 더 측정해 `재측정 편차`에 넣는다.

### 4단계: 분석과 판정 (1~2일)
`일치도`, `요약`, `R2_실측` 탭을 보고 아래 표로 판정한다.

## 4. 통과 기준

| 확인할 것 | 보는 곳 | 통과 기준 | 통과 못 하면 |
|---|---|---|---|
| 사람 A–B 일치도 | `일치도` κ(A–B) | 기준별 κ ≥ 0.6 | 해당 기준의 점수 기준 문구를 고친다. 정의 자체가 애매하면 기준을 합치거나 뺀다 |
| 사람–LLM 일치도 | `일치도` κ(A–LLM), κ(B–LLM) | 기준별 κ ≥ 0.6 | 루브릭 프롬프트를 고친다. 그래도 낮으면 그 기준은 사람 검수를 붙인다 |
| 점수 차이가 큰 건수 | `일치도` "20점 이상 차이" | 기준별 2건 이하 | 해당 응시를 함께 다시 보고 원인을 기록한다 |
| R2 지표 흔들림 | `R2_실측` "흔들림 판정" | 재측정 편차 차이 ≤ 5%p | 실행 횟수를 늘리거나 비교 방식을 바꾼다 |
| 극단 사례 변별 | `요약` "극단 사례 점검" | 극단 사례가 해당 항목에서 60점 미만 | 그 사례를 놓친 하위 기준의 가중치나 점수 기준을 고친다 |
| 응시 1건당 R2 비용 | `R2_실측` "비용" | 팀이 정한 예산 이하 (파일럿 전에 정한다) | 핵심 턴 고르는 기준을 좁히거나 실행 횟수 상한을 낮춘다 |

**참고:** 10건은 κ를 판단하기에 적은 표본이다. 파일럿에서는 κ를 "어느 기준이 문제인지 찾는 신호"로 쓴다. 최종 판단은 20건 확대 후에 한다.

## 5. 역할

| 역할 | 하는 일 |
|---|---|
| 진행자 | 과제와 숨은 테스트 준비, 극단 사례 제작, 응시 진행, 시간 기록, R2 실행 |
| 채점자 A, B | 서로 독립적으로 채점. 극단 사례가 무엇인지 모르는 상태로 채점 |
| LLM 채점 담당 | 루브릭 프롬프트 작성, LLM 채점 실행, 결과 입력 |

채점자와 진행자는 다른 사람이 맡는다. 진행자는 극단 사례를 알고 있어서 채점에 영향을 줄 수 있기 때문이다.

## 6. 비용 관리
- 파일럿 전에 회사별 API 예산 상한을 정하고, `설정` 탭에 가격을 입력한다.
- R2는 핵심 턴만, 2회 실행 후 같으면 멈추는 방식으로 실행한다. 대화 전체를 다시 실행하는 비교는 2~3건만 한다.
- 실행이 끝날 때마다 `R2_실측`의 토큰 수를 채워서 누적 비용을 확인한다.

## 7. 위험 요소

| 위험 | 대응 |
|---|---|
| 표본이 적어 κ가 흔들린다 | 파일럿 κ는 신호로만 쓰고, 20건 확대 후 다시 판단한다 |
| 채점자가 서로 영향을 준다 | 채점이 끝날 때까지 시트를 공유하지 않는다. 각자 사본에 입력하고 진행자가 합친다 |
| LLM 채점이 자기 회사 모델 답변에 후하다 | 가능하면 두 회사 모델로 교차 채점해 차이를 본다 |
| 극단 사례가 너무 뻔하다 | 실제 응시처럼 보이도록 과제 요구사항은 일부 맞추게 만든다 |

## 8. 채점 시트 사용법 요약
- 채점 시트는 Google 스프레드시트로 운영한다. 원본은 진행자만 편집한다.
- **채점자끼리 점수를 보지 않도록 사본을 나눈다.**
  1. 진행자가 원본을 `파일 > 사본 만들기`로 3부 복제한다: `채점_A용`, `채점_B용`, `LLM용`.
  2. 각 사본을 해당 채점자에게만 편집 권한으로 공유한다. 채점자는 자기 이름의 탭(`채점_A` 등)만 채운다.
  3. 채점이 끝나면 진행자가 각 사본의 채점 탭에서 `E2:H81`(점수, 등급, 근거 턴, 메모)을 복사해 원본의 같은 탭 `E2` 위치에 **일반 붙여넣기(Ctrl+V)** 한다. `값만 붙여넣기`는 쓰지 않는다. R2와 D4 점수, 등급 칸은 수식이라 값만 붙여넣으면 수식이 지워진다.
  4. 붙여넣은 뒤 원본의 R2, D4 줄에 점수가 다시 계산되어 나오는지, `요약` 탭에 해당 채점자 점수가 채워졌는지 확인한다.
  5. `R2_실측`과 `응시목록`은 진행자가 원본에 직접 입력한다.
- 노란 칸만 입력한다. 회색 칸은 자동 계산이다.
- `채점_A`, `채점_B`, `채점_LLM` 탭은 구조가 같다. 각 응시마다 R1–R3, D1–D5 8줄이 있다.
- R2와 D4 점수는 직접 입력하지 않는다. R2는 `R2_실측`에서, D4는 `응시목록`의 시간에서 자동으로 계산된다. D4는 D1이 40점 미만이면 0점으로 처리된다.
- 결과는 `요약`(응시별 항목 점수, 극단 사례 점검)과 `일치도`(기준별 κ)에서 본다.

## 9. 파일럿 이후: 사람 채점의 역할

| 시기 | 사람의 역할 | 양 |
|---|---|---|
| 파일럿 | 기준 답안 만들기, 애매한 기준 찾기 | 10~20건, 2명 |
| 운영 시작 후 | 자동 채점 표본 검수 | 응시의 약 5%, 1명 (비율은 운영 규모를 보고 조정) |
| 모델이나 루브릭 프롬프트를 바꿀 때 | 기준 답안 세트로 다시 비교 | 새로 채점하지 않고 파일럿 데이터 재사용 |
| 응시자나 기업이 점수에 이의를 제기할 때 | 해당 응시를 직접 다시 채점 | 건별 |

**기준 답안 세트 관리**
- 파일럿 응시의 대화 로그, 제출물, 사람 채점 결과(점수와 근거 턴)를 한곳에 보관한다. 기준 문구를 고친 뒤 다시 채점한 결과가 있으면 최종본만 남긴다.
- 모델을 바꾸거나 루브릭 프롬프트를 고치면, 바꾼 자동 채점을 이 세트에 돌린다. 사람–LLM κ가 §4 기준 아래로 떨어지면 반영하지 않는다.
- 새 과제를 추가할 때는 그 과제로 5건 정도를 사람이 채점해 세트에 더한다. 과제마다 채점이 어려운 지점이 다르기 때문이다.

**운영 표본 검수**
- 매달 자동 채점된 응시 중 일부를 무작위로 골라 사람 1명이 채점한다. 극단 점수(등급 S 또는 C)는 별도로 몇 건 더 뽑는다.
- 사람과 자동 채점의 등급이 다른 건은 원인을 기록하고, 같은 원인이 반복되면 루브릭 프롬프트를 고친다. 고친 뒤에는 기준 답안 세트로 다시 확인한다.

웹 채팅 대신 pAIr 화면에서 실제 AI 어시스턴트와 함께 과제를 풀고, 재현성과 AI 결과 도출력 점수까지 받을 수 있다.

**준비**
- 환경 변수: `OPENAI_API_KEY`(어시스턴트), `ANTHROPIC_API_KEY`(채점). 키는 저장소에 두지 않는다.
- Java 21(JDK), Node 22

**실행**
1. 백엔드: 저장소 루트에서 `backend\gradlew.bat -p backend bootRun` (포트 8180)
