# 평가 기준 기획안: 재현성 / AI 결과 도출력

## Context
프로그래머스 AI 역량평가의 6개 항목(AI 기초 이해력, AI 활용력, AI 통제력, 재현성, AI 결과 도출력, 성과 잠재력)을 pAIr에 벤치마킹한다. 이 문서는 내 담당인 **재현성**과 **AI 결과 도출력** 두 항목의 정의, 하위 기준, 점수 구간, 측정 데이터를 정한다.

pAIr에서 이미 기록하는 것들을 측정 근거로 쓴다. 대화 턴(`#T07`), 파일 저장과 실행 결과, 체크포인트와 분기(복기 트리), 제출물, 후속 질문 3문항이다(DESIGN.md §6.8, 6.11, 6.13, 7-3). 과제 유형은 개발(Spring Boot + React)과 비개발(기획서, 리포트) 두 가지이므로, 모든 기준에 유형별 측정 방법을 함께 적는다.

**현재 5개 항목과 겹치는 부분 (팀 공유 필요)**
- `결과물 품질(quality)`은 AI 결과 도출력에 흡수된다.
- `검증(verify)`은 AI 통제력(다른 담당자 항목)과 겹친다. 그래서 도출력에서는 "AI 산출물을 걸러내 통합했는가"만 보고, 검증 행위 자체는 채점하지 않는다.
- 재현성은 기존 5개 항목에 없던 새 항목이다.

---

## 공통 채점 규칙
- 항목당 100점이며, 하위 기준 점수에 가중치를 곱해 더한다.
- 등급 구간은 Score Chip 구간을 그대로 쓴다: **S 80↑ / A 60–79 / B 40–59 / C 40↓**
- 측정 소스는 4종이다.
  - `LOG`: 자동 로그 지표
  - `RUN`: 숨은 테스트나 리플레이 실행
  - `JUDGE`: LLM 채점(루브릭 프롬프트 + 근거 턴 인용 필수)
  - `FQ`: 후속 질문 답변
- 모든 감점과 가점에는 근거 턴 번호나 파일을 1개 이상 달아야 한다. 리포트의 인용 블록과 결정적 순간 마커에 그대로 쓰기 위해서다.

## 1. 재현성 (Reproducibility)

**정의:** 응시자가 얻은 결과가 우연이 아닌지를 본다. 같은 과정을 다시 밟으면(본인이든 제3자든, AI를 다시 실행하든) 같은 품질의 결과가 나오는 체계적인 과정인가를 평가한다.

| # | 하위 기준 | 가중치 | 무엇을 보나 | 측정 |
|---|---|---|---|---|
| R1 | 지시 명세성 | 35 | 프롬프트에 목표, 입력 맥락, 제약, 출력 형식, 완료 조건이 명시되어 있는가. 길이가 아니라 **필요 정보를 얼마나 덮었는지**를 본다 | JUDGE (턴별 5요소 체크 → 핵심 턴 평균) |
| R2 | 출력 안정성 | 40 | 최종 결과물에 쓰인 핵심 턴을 응시 때와 같은 회사, 모델, 요청 설정으로 다시 실행했을 때 핵심 산출물이 일관되게 나오는가 (2회부터 시작, 결과가 다르면 최대 5회) | RUN: 개발은 다시 나온 산출물의 숨은 테스트 통과율 평균과 편차, 비개발은 핵심 주장과 수치의 일치율(작은 모델 또는 임베딩 유사도). 자세한 방식은 §3 "R2 다시 실행 방식" |
| R3 | 과정 일관성 | 25 | 같은 종류의 요청에 같은 방식을 쓰는가(템플릿화, 재사용). 후속 질문에서 설명한 절차가 실제 로그와 일치하는가 | LOG(유사 요청 간 구조 유사도) + FQ↔LOG 대조(JUDGE) |

> **과정 기록 기준을 뺀 이유 (2026-11-10):** 혼자 보는 시험에서는 결과를 넘겨받을 사람이 없어 기록 행동을 공정하게 평가하기 어렵다. 또 NOTES.md는 과제 요구사항이면 D1에서, 테스트 작성은 AI 통제력(검증)에서 이미 채점된다. 그래서 재현성은 응시 기록으로 객관적으로 확인할 수 있는 지시 명세성, 출력 안정성, 과정 일관성만 본다.

**등급 서술 (요약)**
- **S:** 핵심 프롬프트만으로 결과가 재생성된다(R2 통과율 편차 ≤10%p). 설명한 절차와 로그가 일치한다.
- **A:** 대부분 재생성되지만 일부 단계가 암묵적이다(대화 밖에서 직접 고친 부분이 있다).
- **B:** 결과가 특정 시도의 운에 기대고 있다(리플레이 편차가 크다). 지시에 핵심 조건이 빠져 있다.
- **C:** 재실행하면 결과가 매번 다르다. 절차를 설명할 수 없거나 로그와 어긋난다.

**보조 지표 (자가진단 전용):** 복기 트리에서 같은 과제의 여러 분기 사이 총점 편차를 "개인 재현성 추이"로 대시보드에 보여준다. 실전 점수에는 반영하지 않는다(분기 수가 사람마다 다르기 때문).

**어뷰징 대응**
- 의미 없는 장문 프롬프트는 R1에서 "불필요 정보 비율"로 감점한다.
- 에디터에서 직접 고친 내용은 R2 리플레이에 반영되지 않는다. 그래서 수작업 수정 비중이 높으면 R2가 자연스럽게 낮아진다. 이것은 의도된 설계다.

## 2. AI 결과 도출력 (AI Result Delivery)

**정의:** AI를 활용해 **요구사항을 충족하는 최종 결과물을 제한 시간 안에 실제로 만들어내는 능력**이다. "좋은 대화"가 아니라 "쓸 수 있는 결과"를 본다.

| # | 하위 기준 | 가중치 | 무엇을 보나 | 측정 |
|---|---|---|---|---|
| D1 | 요구사항 충족 | 35 | 필수 요구사항을 만족하는가 | RUN: 개발은 숨은 테스트 통과율(필수/선택 가중), 비개발은 필수 항목 체크리스트 충족률(JUDGE) |
| D2 | 결과물 완성도 | 20 | 엣지 케이스, 구조, 가독성, 실무 투입 가능성 | 개발: 정적 분석 + JUDGE. 비개발: 논리 구조, 근거, 형식(JUDGE) |
| D3 | AI 산출물 통합력 | 20 | AI 출력을 그대로 붙이지 않고 과제 맥락에 맞게 취사선택하고 수정해 통합했는가. AI의 오답이 최종본에 남았는가 | LOG: AI 응답 블록과 최종 파일의 diff(채택률, 수정률), AI 오류 잔존 여부(JUDGE) |
| D4 | 도출 효율 | 15 | 첫 유효 결과(테스트 첫 통과, 초안 완성)까지 걸린 시간과 턴 수, 막다른 길에서 빠져나온 시간 | LOG: 과제별 응시자 분포의 백분위로 정규화 |
| D5 | 결과 설명력 | 10 | 결과물을 자기 말로 설명하고, 채택하지 않은 AI 제안과 그 이유를 말할 수 있는가 | FQ(JUDGE) |

**등급 서술 (요약)**
- **S:** 필수 요구사항을 100% 충족한다. AI 제안을 선별하고 수정해 통합했고 오류가 남아 있지 않다. 상위 25% 효율이고, 결과를 근거와 함께 설명한다.
- **A:** 필수 요구사항을 충족하지만 완성도나 효율에서 일부 아쉽다.
- **B:** 일부 필수 요구사항이 빠졌다. AI 출력을 거의 그대로 붙였다.
- **C:** 제출물이 동작하지 않거나 요구사항에서 벗어났다. AI 오답이 그대로 남아 있다.

**가드레일**
- D4 효율은 D1이 B 이상일 때만 점수를 준다. 빠르지만 틀린 결과에 효율 점수를 주지 않기 위해서다.
- D3에서 "채택률이 낮을수록 좋다"는 식으로 채점하지 않는다. 기준은 오류 잔존 여부와 맥락 적합성이다.

### R2 다시 실행 방식 (OpenAI, Anthropic 공통)

대화 전체를 여러 번 다시 실행하면 응시 1건에 수십만 토큰이 들 수 있다. 아래 방식으로 검증 품질은 유지하면서 호출량을 줄인다.

**1. 무엇을 다시 실행하나: 핵심 턴만**
- 대화 전체가 아니라, AI 답변이 최종 제출물에 실제로 쓰인 턴만 다시 실행한다(보통 2~4턴).
- 어떤 턴인지는 D3에서 이미 계산하는 "AI 응답 블록과 최종 파일의 diff"로 고른다. 추가 비용이 없다.
- 그 턴 앞의 대화는 기록된 그대로 고정하고, 그 턴의 답변만 새로 받는다.

**2. 몇 번 실행하나: 2번 해보고 같으면 멈춤**
- 핵심 턴마다 2회 실행한다. 두 결과가 같으면(아래 비교 기준) 안정적으로 보고 끝낸다.
- 다르면 최대 5회까지 늘려 편차를 잰다.
- 자가진단은 기본 2회만 실행하고, 결과가 다를 때만 늘린다.

**3. 어떤 모델로 실행하나: 응시 때와 같은 회사, 같은 모델**
- 턴마다 기록한 회사와 모델 ID로 다시 실행한다. 다른 회사나 다른 모델로 바꿔 실행하지 않는다(결과가 다른 게 당연해 비교 의미가 없다).
- **시험마다 모델을 하나로 고정하는 것을 기본으로 한다.** 응시자가 모델을 고르면 R2 점수가 사람보다 모델 성향에 좌우된다. 선택을 허용하는 시험은 R2 점수를 같은 모델 사용자끼리만 비교한다.
- temperature나 시드를 고정하는 방식은 쓰지 않는다. 최신 Claude 모델은 temperature 같은 값을 보내면 오류가 나고, OpenAI의 시드 기능은 지원 범위를 확인하지 못했다. 대신 **응시 때 보낸 요청 설정(모델, 추론 강도, 시스템 프롬프트 등)을 원문 그대로 재사용**한다.

**4. 결과를 어떻게 비교하나: 토큰을 거의 안 쓰는 방식 우선**
- 개발 과제: 다시 나온 코드를 숨은 테스트로 돌려 통과 여부를 비교한다. LLM 호출이 없다.
- 비개발 과제: 큰 모델 채점 대신 작은 모델이나 임베딩 유사도로 핵심 주장과 수치가 같은지만 본다.
- 다시 실행할 때 답변 길이에 상한을 둬서 필요한 산출물만 받는다.

**5. 언제 실행하나: 응시 후 배치로**
- 채점은 실시간이 아니어도 되므로 두 회사 모두 배치 API로 보낸다(일반 요청의 50% 가격, 최대 24시간 안에 결과 반환).
- 실전 시험은 결과를 기업이 나중에 받으므로 영향이 없다.
- 자가진단 리포트는 R2 결과가 들어오기 전까지 "재현성 계산 중"으로 표시했다가 나중에 채운다.

**회사별 비용 절감 수단 비교**

| | Anthropic | OpenAI |
|---|---|---|
| 배치 할인 | 50% | 50% |
| 결과 반환 | 최대 24시간 | 최대 24시간(창 24h 고정) |
| 프롬프트 캐싱 | 요청에 직접 지정. 캐시 읽기는 입력 가격의 약 10% | 1,024토큰 이상이면 자동. 캐시된 입력 50% 할인 |
| 배치와 캐싱 동시 적용 | 별도 확인 필요 | 확실하지 않음(예전 문서에는 불가로 알려짐). 목업으로 실측 |

- 핵심 턴을 여러 번 다시 실행할 때 앞부분 대화가 똑같으므로 캐싱 효과가 크다. Anthropic은 캐시 지정 위치를 핵심 턴 직전에 둔다.
- 위 가격 조건은 2026-11-10 기준 확인 내용이며, 실제 운영 전 각 회사의 최신 가격 페이지로 다시 확인한다.

## 4. 후속 질문 문항 뱅크 (예시)
- 재현성: "동료가 같은 결과를 얻으려면 어떤 지시를 어떤 순서로 주면 되나요?" / "이 결과가 맞다는 것을 다음에도 확인할 수 있게 무엇을 남겼나요?"
- 도출력: "AI 제안 중 채택하지 않은 것과 그 이유는?" / "제출물에서 가장 자신 없는 부분과 그 이유는?"

## 5. 리포트 화면 반영
- 항목별 막대 리스트에 두 항목을 추가하고, 하위 기준(R1–R3, D1–D5)은 펼침으로 보여준다.
- 결정적 순간 마커 후보는 두 가지다. R2 편차를 크게 만든 턴(caution), D3에서 AI 오류를 걸러낸 턴(signal).

## 6. 기준 검증 방법 (Verification)
1. 목업 응시 20건(개발 10, 비개발 10)을 사람 2명과 LLM 채점으로 동시에 채점한다. 사람 간, 사람-LLM 간 일치도는 Cohen's κ ≥ 0.6을 목표로 한다.
2. R2 리플레이를 같은 응시에 2번 돌려 지표 자체의 흔들림을 확인한다(편차 ≤5%p).
   - 같은 20건으로 응시 1건당 R2 토큰 사용량과 비용을 회사별로 실측한다. "2번 해보고 멈춤"으로 끝난 비율도 함께 기록한다.
   - 핵심 턴만 다시 실행한 R2와 대화 전체를 다시 실행한 R2를 몇 건 비교해, 줄인 방식이 판정을 바꾸지 않는지 확인한다.
3. 극단 사례로 점검한다: 장문 프롬프트만 쓴 응시, AI 출력 전체 복붙 응시, 수작업 위주 응시가 의도대로 낮게 나오는지 확인한다.
