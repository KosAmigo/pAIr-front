# pAIr-front 실기기 시험 체크리스트 (1~5단계 한꺼번에)

작성일: 2026-11-21

근거 문서
- `docs/plan/proctor-client-analysis-plan.md`

자동 점검은 모두 통과했지만, 실제 휴대폰 시험은 이번이 처음이다. 코드에서 확인하지 못한 것은 "확인 필요"로 표시했다. 시험하면서 `- [ ]`를 `- [x]`로 바꿔 표시한다.

## 0. 사전 점검 결과 (2026-11-21 실행)

| 명령 | 결과 |
|---|---|
| `npm --prefix frontend run test:proctor` | 통과 141개, 실패 0 (같은 날 책상 감지 경고 변경 뒤 재실행: 통과 142개, 실패 0) |
| `npm --prefix frontend run test:scripts` | 통과 9개, 실패 0 |
| `npx tsc -b` | 통과. 루트에는 tsconfig가 없어 `pAIr-front/frontend`에서 실행 |
| `npm --prefix frontend run build` | 통과. 500kB 초과 청크 경고만 있음 |

- 빌드를 돌려서 `frontend/dist`가 새로 만들어졌다. 소스 변경은 없다.
- 환경 점검(`EnvCheckPanel`)에 "테스트용 건너뛰기"가 있다. 개발 서버(`import.meta.env.DEV`)에서만 동작하고, 건너뛰면 감독 패널이 안 뜬다. **건너뛰지 말고 진행한다.**

## 1. 준비

**문서와 코드가 다른 점**
- 끊김 유예는 **15초**다 (`connectionPolicy.ts`). 계획서의 10초가 아니다.
- 휴대폰 무응답(stale) 판정은 서버 기준 **15초**다 (`phoneStale.ts`). API 문서 2-4절도 15초로 맞췄다.
- 서버 쪽 연결 유예는 별개로 **5분**이다 (시험 화면이 10초마다 `heartbeat`, 90초 넘는 끊김은 `CONNECTION_LOST`, 5분 넘으면 링크 만료 `LINK_EXPIRED`). 프론트의 15초 차단과 다른 층이다 (명세서 §5.10).
- 서버 재확인(4단계) 배지는 프론트만 구현돼 있다. 5단계 감독관 영상은 시그널링이 개발 릴레이로만 된다.

**서버**
- [ ] 두 저장소가 있는 상위 폴더(`C:\dev\pAIr`)에서 `node pAIr-front/scripts/dev-all.mjs`를 실행한다. 터널·백엔드(8180)·프론트(5173)가 함께 뜬다.
- [ ] 터미널에 `https://○○○.trycloudflare.com` 주소가 나오는지 본다. 안 나오면 `cloudflared` 설치(`winget install Cloudflare.cloudflared` 후 터미널 재시작)가 필요하다.
- [ ] **터널 주소는 켤 때마다 바뀐다.** 서버를 다시 켜면 초대 메일을 **새로 보낸다.** 메일 링크와 QR이 그 주소로 만들어진다.
- [ ] 터널 모드는 프론트를 빌드본(`vite preview`)으로 띄운다. 빌드를 먼저 해 두라는 안내가 있는지는 **확인 필요**.
- [ ] 감독관 시험(H)용으로 PC 브라우저 창을 하나 더 열고 콘솔에 감독관·관리자로 로그인한다. 응시자 창과는 다른 프로필이나 시크릿 창을 쓴다.

**준비물**
- [ ] PC: 웹캠, 크롬 또는 엣지 최신판(화면 공유를 지원하는 브라우저). 모니터는 가능하면 2대(E항목의 "창만 공유" 시험용).
- [ ] 아이폰: LTE(와이파이 끔), 충전 케이블, 거치대. 책·실제 휴대폰 1대 더·메모지를 책상에 준비한다.
- [ ] 아이폰 Safari 주의: 화면 자동 꺼짐은 `wakeLock`으로 막는다. 그래도 설정에서 자동 잠금을 "안 함"으로 바꾸고, **페이지는 앞에 띄운 채로** 둔다. 다른 앱으로 가면 경고가 발생한다(`visibilitychange`).
- [ ] 시험 시작 전 서버 PC에서 `%TEMP%\pair-relay.log`가 생기는지 확인한다(`dev-all`을 켠 PC에 쌓인다).

## 2. 시나리오별 항목

각 항목은 **방법 → 기대 → 실패하면 볼 곳** 순서다.

### A. 휴대폰 연결과 안정성
- [ ] **A1.** PC에서 터널 주소로 입장해 환경 점검의 휴대폰 단계까지 간다. 아이폰 와이파이를 끄고 QR을 찍어 "보조 캠 시작"을 누른다. → 휴대폰 화면에 "영상 송신 중", PC 카드에 영상이 나온다. 실패하면 README "안 될 때" 표(`Blocked request`, QR 주소가 192.168…, LTE에서 영상 없음=TURN 필요)와 릴레이 로그를 본다.
- [ ] **A2.** 휴대폰 화면에 "다시 불러와졌습니다" 안내가 **뜨지 않는지** 본다. → 안 뜨는 게 정상이다. 뜨면 어느 단계("카메라 준비" 또는 "영상 송신")에서 새로고침됐는지 기록한다 (`PhoneCamPage.tsx`의 `pair.phone.lastPhase`).
- [ ] **A3.** 감시를 10분 이상 유지한다. 그동안 휴대폰은 앞화면, 충전기 연결 상태로 둔다. → 영상이 끊기지 않고, 페이지가 닫히거나 새로고침되지 않고(이전 증상은 약 10초 뒤 1006 종료), PC에 "휴대폰 연결 끊김" 경고가 안 뜬다. 실패하면 릴레이 로그의 `stale 판정`, `폰 신호 간격 …ms`, `폰 보고 … 재연결 N회, 마지막 닫힘 code …, 타이머 최대 지연 …ms`를 본다.
- [ ] **A4.** 10분 동안 아이폰을 손으로 만져 본다. 발열, 배터리 감소, 화면 꺼짐 여부를 기록한다. → 이전 구조보다 덜 뜨거워야 한다(모델·추론이 휴대폰에서 빠졌음). 수치 기준은 없어서 **확인 필요**.
- [ ] **A5.** 휴대폰에서 홈 버튼으로 다른 앱으로 나갔다 돌아온다. → 나가는 순간 `PHONE_DISCONNECTED`("휴대폰에서 감독 화면을 벗어났습니다") 경고가 PC 최근 경고에 남는다.
- [ ] **A6.** 휴대폰 Wi-Fi/LTE를 5초쯤 껐다 켠다. → 재연결 후 영상이 다시 나온다. 이 동안 영상 재요청이 최대 3회 자동으로 이뤄진다(`peerLink.ts`).

### B. PC의 휴대폰 영상 분석과 이벤트
전제: 환경 점검 통과 후 감시가 시작됐고, PC 패널에 "휴대폰 보조 캠 연결됨 · 감시 중"이 보여야 한다. 보정은 PC에서 3초 걸리며 양손이 보이는 위치에서 잡는다.
- [ ] **B1.** 보정 중에 휴대폰을 세워 **두 손이 키보드 위에 보이게** 한다. → "기준 위치 잡는 중" 뒤 "감시 중"으로 바뀐다. 손이 한 번도 안 보이면 오류 창이 뜨고 "휴대폰 기준 다시 잡기" 버튼이 나온다.
- [ ] **B2.** 두 손을 모두 화면 밖으로 3초 이상 뺀다. → "손이 화면 밖으로 벗어났습니다" 경고(`HAND_MISSING`). 규칙: 3초 지속, 8초 쿨다운.
- [ ] **B3.** 한 손만 마우스 쪽으로 옮겨 쓰거나, 키보드에서 마우스로 손을 옮긴다. → **경고가 없어야 한다.** 양손이 모두 사라질 때만 경고한다.
- [ ] **B4.** 책상 위에 다른 휴대폰을 1초 이상 올린다. → `PHONE`("휴대폰이 감지되었습니다"). 책을 1.5초 이상 → `BOOK`. 노트북·TV 같은 다른 화면 1.5초 이상 → `EXTRA_SCREEN`. 쿨다운은 각 10초.
- [ ] **B5.** 같은 감지를 여러 번 반복해 오탐·미탐을 센다(조명 어두운 조건 포함). → 기준 수치가 문서에 없어서 비율은 직접 기록한다. 휴대폰 영상 분석 간격은 최소 200ms(5회/초)다.
- [ ] **B6.** PC 작업 관리자에서 브라우저 CPU 점유율을 보고, 웹캠 분석·휴대폰 분석이 동시에 돌 때 PC 입력이 끊기는지 본다. → 저사양 PC는 부족할 수 있다. 계획서에 Web Worker 분리가 후보로 적혀 있다.
- 실패하면 PC 감독 패널의 "지금 이어지는 이상 상태"(몇 초/몇 초)와 `phoneAnalysis.ts` 상태(`error`)를 본다.

### C. 환경 점검 (조명·책상 스캔)
- [ ] **C1.** 휴대폰 단계에서 방을 어둡게 한다. → 조명 항목이 경고/실패로 나오고, 어두울 때 휴대폰 손전등 요청이 한 번 간다. 끝나면 꺼진다.
- [ ] **C2.** 책상 스캔 안내문("휴대폰을 책상 전체가 한 화면에 보이는 곳에 세워 두고 움직이지 마세요")이 뜬다. 휴대폰을 손에 들고 흔들다가 거치대에 고정한다. → 흔들리는 동안 대기, 안 흔들리고 1.5초 지나면 시작한다. 끝내 고정이 안 되면 **15초 뒤 그대로 시작**한다.
- [ ] **C3.** 휴대폰이 고화질로 바뀌는지 본다("휴대폰 영상을 고화질로 바꾸는 중입니다"). → 최대 5초 기다리며, 가로 해상도 1200 이상이면 충분하다. 안 되면 그대로 진행되는지 **확인 필요**.
- [ ] **C4.** 책상에 휴대폰·책을 올려 둔 채 스캔한다. → 확인 창 없이 책상 항목이 **경고(주의)** 로 끝나고, 결과 문구에 "책상 위에서 휴대폰 N회, 책 N회가 감지되었습니다. 시험에 필요 없는 물건은 치워 주세요 … 감독관에게 전달됩니다"가 나온다. 점검은 통과로 처리되어 응시가 막히지 않는다("주의 항목은 감독 기록에 남습니다" 문구). 사진과 감지된 물체 목록이 감독관 콘솔의 환경 점검 사진에 보인다. (2026-11-21 변경: 이전에는 "이상 없음"으로만 보였다)
- [ ] **C5.** 책·메모를 올린 채 스캔한다. → 감지된 물체가 있으면 위와 같은 경고와 감독관 콘솔 사진의 물체 목록에 나오고, 아무것도 안 잡히면 "감지된 물체 없음"으로 통과한다(책·메모는 모델 감지 대상이 아닐 수 있어 **확인 필요**).
- [ ] **C6.** 스캔 도중 휴대폰 영상을 끊는다. → "스캔 도중 휴대폰 영상이 끊겼습니다. 연결을 확인하고 다시 점검해 주세요."가 뜬다.
- [ ] **C7.** 책상 스캔 결과로 응시가 막히는지 본다. → 휴대폰·책이 잡혀도 "치운 뒤 다시 스캔" 안내나 확인 창 없이 다음 단계로 간다.
- [ ] **C8.** 시작 10분 전 이후에 새 초대 링크로 입장한다(시작 시각을 곧 오도록 잡은 회차). → "대기실 입장 시간이 지났습니다" 안내가 나오고 점검·대기실로 가지 못한다. 시작 10분 전 이전에 열면 입장 화면에 "HH:MM까지 대기실 입장" 줄이 보인다. 점검 도중 마감을 넘기면 대기실에서 같은 안내로 막힌다. ("점검 건너뛰기" 환경은 예외)
- [ ] **C9.** (2026-11-21 추가) 일부러 한 항목(예: 귀 확인을 일부러 건너뛰거나 책상에 책을 올려 경고)만 통과하지 못하게 한 뒤 "통과하지 못한 항목만 다시 (n)"를 누른다. → 이미 통과한 항목(브라우저·모니터·카메라·소음·조명 등)과 그 사진은 그대로 두고, 통과하지 못한 항목만 다시 진행한다. 책상 스캔만 다시 해도 분석 모델을 다시 내려받지 않고 바로 시작한다. "처음부터 다시"는 전부 다시 한다.
- 실패하면 `deskScan.ts`(타일 감지, 고정 판정), `EnvCheckPanel.tsx`(항목별 건너뛰기), `models.ts`(스캔 감지기 재사용)와 환경 점검 항목별 detail 문구를 본다.

### D. 연결 필수
- [ ] **D1.** 환경 점검 후 웹캠, 휴대폰, 화면 공유 중 하나라도 빠진 상태에서 시험을 시작해 본다. → "응시 시작" 버튼이 비활성(`channelsReady`)이다.
- [ ] **D2.** 응시 중 휴대폰 영상만 끊는다(예: 휴대폰 앱 종료). → 상단에 "휴대폰 캠 연결이 끊겼습니다. N초 안에 다시 연결해 주세요."가 나온다.
- [ ] **D3.** 15초 안에 다시 연결한다. → 끊김으로 치지 않고 경고가 사라진다. 15초를 넘기면 "연결이 끊겨 시험이 일시 중지되었습니다" 전체 화면 창이 뜨고, 끊긴 채널 안내가 나온다.
- [ ] **D4.** 차단 중에 휴대폰만 다시 연결한다. → **세 채널이 모두 돌아와야** 풀린다. 풀리면 응시 화면이 그대로 이어진다.
- [ ] **D5.** 웹캠을 USB에서 뽑았다가 꽂는다. → 차단 창에 "웹캠 다시 연결" 버튼이 나온다. 화면 공유를 "공유 중지"하면 차단 창에서 다시 시작할 수 있다.
- [ ] **D6.** 차단 중 시간이 흐르는지 본다(시험 타이머가 멈추는지는 코드에서 **확인 필요**).
- 실패하면 `connectionPolicy.ts`(유예, 차단 로직), `ConnectionGate.tsx`를 본다.

### E. PC 화면 공유
- [ ] **E1.** 동의 문구를 확인한다. → 4줄이다. 녹화·저장하지 않음, 감독관이 열 때만 실시간 전송, 이벤트 순간 흐린 한 장만 저장, **"전체 화면"을 고르라**는 안내.
- [ ] **E2.** 공유 팝업에서 "전체 화면"을 고른다. → 연결됨. 이번엔 "창" 또는 "탭"만 고른다. → "전체 화면이 아닌 창·탭만 공유했습니다. 다시 시작해서 '전체 화면'을 선택해 주세요."가 뜨고 연결로 치지 않는다(시험 시작 불가).
- [ ] **E3.** 응시 중 브라우저의 "공유 중지" 버튼을 누른다. → `SCREEN_STOPPED`가 PC 최근 경고에 남고 D항목의 끊김 규칙이 적용된다.
- [ ] **E4.** 응시 중 화면을 창만 공유로 바꿔 본다(가능하면). → `SCREEN_PARTIAL` 기록.
- [ ] **E5. 중요**: 화면 공유 이벤트는 지금 **서버로 가지 않는다.** `SCREEN_EVENTS_ACCEPTED=false`(`screenContract.ts`)라서 PC 화면 로그에만 남고, 흐린 사진도 이 상태에서는 만들지 않는다. "이벤트 순간 흐린 사진이 서버에 저장되는지"는 백엔드가 `SCREEN`을 받기 전에는 시험할 수 없다(3절 참고). 흐림 처리 자체(가로 96px)는 단위 테스트 `screen.test.ts`로만 확인돼 있다.

### F. 사전 테스트 (`/practice`)
- [ ] **F1.** 로그인 없이 `터널주소/practice`로 들어간다. → "사전 테스트" 화면, 환경 점검과 휴대폰 QR, 화면 공유 카드, 연결 상태가 나온다.
- [ ] **F2.** 휴대폰으로 QR을 찍어 연결하고 환경 점검을 통과한다. → "사전 테스트를 통과했습니다…" 문구가 나온다(세 채널 연결 + 점검 통과 시).
- [ ] **F3.** 연습 중 손 이탈 등을 일으켜 본다. → 서버·콘솔에 이벤트, 사진, 점검 결과가 **하나도 안 남아야** 한다(`camHub.connectPractice`). 콘솔에서 해당 회차가 아무 기록도 없는지 확인한다. 사전 테스트에서는 `recordScreen`도 아무것도 남기지 않는다.
- [ ] **F4.** "연습 끝내기"를 누른다. → 홈으로 이동한다.
- 확인 필요: 사전 테스트가 "시험 7일 전부터 열린다"는 제한은 계획 가정일 뿐, 코드에서 확인하지 못했다(지금은 공개 페이지라 언제든 열림).

### G. 서버 확인 배지
- [ ] **G1.** 응시자 이벤트(B항목)가 쌓인 뒤 감독관 콘솔 감독 패널(`ProctorPanel`)을 연다. → 지금 백엔드는 `serverCheck` 필드가 없어서 **배지가 하나도 안 보이고, 화면이 정상이면 합격**이다. "서버 미확인 N건" 머리글도 안 보여야 한다.
- [ ] **G2.** 이벤트 목록에 사진이 붙어서 열리는지 본다(`snapshot: ok`). → 영상 이벤트(PC_CAM, PHONE_CAM)에는 사진이 붙어 간다.
- 배지가 실제로 바뀌는 것(PENDING→CONFIRMED/UNCONFIRMED)은 백엔드 구현 뒤에야 확인할 수 있다.

### H. 감독관 영상 보기
- [ ] **H1.** 응시자가 감시 중인 상태에서 다른 창으로 감독관 로그인, 콘솔 감독 패널의 그 응시자 행에서 "영상 보기"를 누른다. → 안내 문구("열 때만 응시자 PC가 영상을 보냅니다. 영상은 저장되지 않습니다.")가 있고, 열면 휴대폰·웹캠·화면 3채널이 순서대로 연결 중 → 라이브로 바뀐다.
- [ ] **H2.** 영상이 뜬 상태에서 감독관 화면의 "영상 닫기"를 누른다. → 응시자 PC의 감독관 전송이 멈춘다. 릴레이 로그에 `unwatch … (남은 감독관 0)`이 남는다. 응시자 PC의 CPU도 내려가야 한다.
- [ ] **H3.** 감독관이 영상을 안 열었을 때 응시자 PC가 영상을 보내지 않는지 본다. → 로그에 `watch`가 없어야 한다.
- [ ] **H4.** 감독관 창 2개로 같은 응시자를 연다 → 둘 다 열림. 3번째 창 → "보고 있는 감독관이 너무 많습니다"(`full`, 상한 2명). 한 명이 닫으면 다시 들어간다.
- [ ] **H5.** 응시자 PC를 새로고침(또는 끊음). → 감독관 화면에 "응시자 PC가 연결돼 있지 않습니다. 연결되면 자동으로 이어집니다."가 뜨고, 응시자 PC가 돌아오면 자동 재연결된다.
- [ ] **H6.** 일부러 휴대폰 영상만 끊어 둔 채 보기 → 그 채널은 "영상 없음"(unavailable)이어야 한다.
- [ ] **H7.** 다른 회사 감독관, 로그인 없음, 응시자 본인이 `watch`하면 `denied`인지. → 개발 릴레이는 로그인 헤더로 백엔드 `GET /api/console/sessions/{id}`를 불러 권한을 확인하는 **임시 방식**이다. 다른 회사 계정이 준비돼 있어야 시험할 수 있다.
- [ ] **H8.** 영상이 서버에 저장되지 않는지. → 서버·DB에 영상이 남지 않아야 한다. 개발 릴레이는 시그널링만 넘기고 영상은 PC↔감독관 P2P다. LTE처럼 직접 연결이 막히는 망에서는 TURN이 필요하다(**H에서 영상이 안 나오면 TURN 가능성**).
- [ ] **H9.** 응시자 화면의 동의 문구에 "감독관이 보는 동안 화면에 표시됩니다" 안내가 있고, 응시자가 보고 있는 감독관 수를 화면에서 볼 수 있는지는 코드에서 **확인 필요**.

### I. 브라우저 이벤트와 PC 감독 패널
- [ ] **I1.** 응시 중 다른 탭으로 이동, 창을 클릭해 포커스 이탈, 마우스를 창 밖으로, 전체화면 해제, 외부 텍스트 붙여넣기를 각각 해 본다. → `TAB_HIDDEN`, `WINDOW_BLUR`, `MOUSE_LEAVE`, `FULLSCREEN_EXIT`, `PASTE`가 기록된다.
- [ ] **I2.** 응시자 PC 오른쪽 감독 패널의 "최근 경고" 목록(최대 5개, 시각·출처 라벨·문구)에 PC 웹캠 경고와 **휴대폰 경고(B 항목, A5)가 함께** 나오는지 본다.
- [ ] **I3.** 웹캠 이벤트도 확인한다: 얼굴 가리기(`NO_FACE`), 두 사람(`MULTI_FACE`), 고개 돌림, 오래 숙임, 시선 이탈, 몸 돌림.
- [ ] **I4.** 감독관 콘솔 이벤트 목록에도 같은 이벤트가 나오고, 휴대폰 이벤트는 `source=PHONE_CAM`으로 저장되는지 본다.

## 3. 백엔드가 구현돼야 확인할 수 있는 것

| 항목 | 지금 상태 | 확인 방법 (백엔드 준비 후) |
|---|---|---|
| 서버 재확인 (`serverCheck`·`serverCheckedAt`) | 프론트 배지·정렬만 구현, 백엔드 필드 없음 | API 문서 6-10절 7개 항목 |
| 화면 공유 사진 `source=SCREEN`, `SCREEN_STOPPED`·`SCREEN_PARTIAL` | 프론트는 `SCREEN_EVENTS_ACCEPTED=false`로 전송 막음 | 백엔드 구현 후 `true`로 바꾸고 E항목 재시험 |
| 분석 중단 감지 (`heartbeat`에 `analysis` 필드) | 제안만, 프론트도 안 보냄 | 6-7절 |
| 감독관 시그널링·권한·열람 기록 | 개발 릴레이(`proctorRelay.ts`) 임시 구현. 로그인 헤더를 메시지에 실음 | 운영 Spring WebSocket에서 6-11절 7개 항목 |
| 운영 릴레이 | 개발 릴레이만 있음 | 동일 동작을 Spring WebSocket으로 |
| 3채널 끊김 이벤트 유형 | 서버가 만드는 끊김은 `PHONE_DISCONNECTED`뿐 | 백엔드 협의 후 |

**지금은 개발 릴레이로만 되는 것**: 휴대폰 짝짓기·신호 중계, H항목 전체, 사전 테스트 무기록 처리.

(API 문서 위치: `pAIr-docs/API/실전시험_감독_API.md`)

## 4. 알려진 한계·위험

- 분석이 응시자 PC에서 돌기 때문에 응시자가 분석을 끄거나 막을 수 있다. 탐지 수단(감독관 영상, 서버 재확인, 분석 중단 감지)은 아직 일부만 있다.
- 아이폰은 메모리가 작아 모델이 필요 없어진 대신 영상 송신만 한다. 그래도 10분 이상에서 발열·종료 여부는 A3·A4로 직접 확인해야 한다.
- LTE 터널은 불안정할 수 있다. 터널 주소가 바뀌면 QR과 초대 메일이 무효가 된다.
- 이번 시험은 **응시자 1명** 규모다. 한 회차 300명 이상 동시 접속, 서버 부하, TURN 비용은 검증되지 않는다.
- 감독관 영상은 응시자 PC가 감독관마다 따로 인코딩하므로 상한 2명이다(`watchRoom.ts`).
- 화면 공유 이벤트는 서버에 안 가므로, 화면 이탈은 지금 PC 로컬 로그에만 남는다.

**문제가 생기면 수집할 것**
1. 어느 항목(예: B2, D3)인지와 정확한 시각(시:분:초).
2. `%TEMP%\pair-relay.log` 전체(서버 PC). 시각이 ISO라 휴대폰·PC 화면 시각과 맞춰 볼 수 있다.
3. 화면에 뜬 문구 그대로(스크린샷). 휴대폰은 "다시 불러와졌습니다" 안내의 단계 이름도.
4. 브라우저 개발자 도구 콘솔의 오류(PC, 감독관 창).
5. PC CPU 점유율, 아이폰 발열·배터리 변화, 사용 망(와이파이/LTE).
