# 감독 구조 전환 구현 계획: 응시자 쪽 분석 + 이벤트 사진만 서버 확인

작성일: 2026-11-21

근거 의도 문서
- `docs/intent/proctor-client-analysis.md` (최신 확정 의도)
- (이전 확정 `proctor-3channel` 은 위 의도 문서의 "3채널 확정 내용"으로 합치고 지웠다. 연결 필수·사전 테스트·화면 공유 동의·신분증 제외 포함)

이 문서는 처음에는 계획이었다. **2026-11-21 현재 진행 상태** (아래 2절은 계획 당시의 코드 상태 기록이다):

| 단계 | 상태 |
|---|---|
| 0. 기준선 | 진단 세션 변경 반영 완료 (stale 15초, 릴레이 진단 로그, 프레임 예산) |
| 1. 휴대폰은 송신만, 분석은 PC | ✅ 구현 (`phoneAnalysis.ts`, 릴레이는 `phone-alert` 만 전달) |
| 2. 책상 스캔을 PC로 | ✅ 구현 (`check/deskScan.ts`, 스캔 때만 고화질). 책상 위 감지는 경고만 하고 통과, 다시 점검은 통과하지 못한 항목만 |
| 3. 연결 필수 + 화면 공유 + 사전 테스트 | ✅ 구현 (유예 15초 `connectionPolicy.ts`, `screen/`, `/practice`). 화면 공유 이벤트 서버 전송은 꺼짐 |
| 4. 서버 재확인 | 프론트 배지·정렬만. 백엔드 미구현 |
| 5. 감독관 실시간 영상 | ✅ 프론트·개발 릴레이. 운영 백엔드(시그널링·권한·열람 기록) 미구현 |

실기기 확인은 `real-device-checklist.md` 로 진행한다.

## 1. 사용자 확정 사항

| 항목 | 확정 | 계획에 미치는 영향 |
|---|---|---|
| 서버 재확인이 못 찾은 이벤트 | 버리지 않고 "서버 미확인"으로 기록 | 이벤트 상태 `PENDING / CONFIRMED / UNCONFIRMED`, 콘솔은 미확인도 표시 |
| 영상 실시간 전송 | 감독관이 그 응시자를 열었을 때만 | 상시 전송 없음, P2P로 시작 |
| 책상 스캔 물체 감지 | PC에서 감지 | 휴대폰의 물체 감지기를 완전히 제거, 스캔 때만 고화질 영상을 PC로 전송 |
| 감독관 동시 시청 | 한 명씩만 | SFU 불필요 (응시자 1명에 감독관 몇 명까지 허용할지만 정하면 됨) |
| 순간 끊김 유예 | 10초 (초안 값, 3단계 착수 때 재확인) | 3단계 상수 |
| 사전 테스트 | 실전과 같은 흐름, 기록 없음, 7일 전부터 (초안 값, 3단계 착수 때 재확인) | 3단계 범위 |

## 2. 현재 코드 상태 (2026-11-21 확인)

- 휴대폰(`PhoneCamPage.tsx`)이 손·물체 모델을 올려 분석하고, 경고를 릴레이 `violation`으로 보낸다. 개발 릴레이(`frontend/server/proctorRelay.ts`)가 그 경고를 백엔드 `proctor-events`에 `source=PHONE_CAM`으로 저장한다.
- PC는 이미 휴대폰 영상을 받는다(`camHub.ts`의 `phoneStream`). 다만 미리보기용으로 낮춰 보낸다(400kbps, 10fps, 절반 해상도, `peerLink.ts`). 분석에는 화질이 부족하다.
- PC는 face·pose·hand 모델을 올리지만 `pcFeatures`는 face와 pose만 쓴다(hand 미사용).
- 화면 공유(`getDisplayMedia`)는 코드가 없다. 연결 필수와 사전 테스트도 `proctor/` 안에서 구현이 확인되지 않았다.
- 백엔드는 `proctor-events`와 `env-scan`만 있다. 서버 재확인, 감독관 영상 시그널링은 없다. 개발 릴레이는 PC↔휴대폰 1:1 짝만 지원한다.
- `relay-diagnose` 세션이 `proctorRelay.ts`, `phoneStale.ts`(15초), `relayLog.ts`, `frameBudget.ts`를 고치는 중이다. 1단계는 이 변경이 끝난 뒤 시작한다.

| 1. 휴대폰은 송신만, 분석은 PC | 휴대폰 부하 제거, 분석을 PC가 받은 영상에서 수행 | `PhoneCamPage.tsx`, `peerLink.ts`, `camHub.ts`, `phoneRules.ts`·`RuleEngine.ts`(재사용), `events.ts`, `proctorRelay.ts` | 0 | 휴대폰에 모델·추론 없음. PC가 휴대폰 영상에서 손 이탈·휴대폰·책·화면을 감지해 `source=PHONE_CAM`으로 아웃박스 저장. 휴대폰 CPU·메모리·1006 이전과 비교 |

| 3. 연결 필수 + 화면 공유 + 사전 테스트 | 3채널 모두 연결돼야 응시, 끊기면 차단 | `camHub.ts`, 입장·응시 화면, 화면 공유 동의 문구, 흐린 사진 | 1 | 세 채널 중 하나가 10초 넘게 끊기면 차단, 재연결하면 이어서 응시. 사전 테스트는 기록이 남지 않음 |
| 4. 서버 재확인 | 영상 이벤트 사진을 서버가 한 번 더 확인 | 프론트: 이벤트 전송·상태 표시. 백엔드: 5절 계약 | 1, 백엔드 합의 | 이벤트에 `PENDING/CONFIRMED/UNCONFIRMED`가 붙어 콘솔에 표시 |
| 5. 감독관 실시간 영상 | 감독관이 연 응시자 영상만 전송 (P2P) | 응시자 송신, `ProctorPanel.tsx` 시청 UI, 시그널링 | 3, 백엔드 합의 | 감독관이 열면 3채널이 보이고 닫으면 전송 중단, 영상 저장 없음 |

순서 메모
- 3단계는 4·5단계와 독립이라 1단계 뒤에 병행할 수 있다.
- 4단계 백엔드 협의(모델·인프라)는 시간이 걸리므로 지금 시작해도 된다.
- 브라우저 이벤트는 이미 바로 기록되므로 따로 구현할 것이 없다.

## 4. 프론트·백엔드 분담

- 프론트 단독 가능: 1, 2, 3단계 전부, 4단계의 송신·표시, 5단계의 응시자 송신과 시청 UI (서버 시그널링 전에는 개발 릴레이를 임시 확장해 시연)
- 백엔드 합의 필요: 서버 재확인, 화면 공유 사진 저장, 감독관 시그널링, 운영 릴레이, 3채널 끊김 이벤트 유형

## 5. 백엔드 요청 계약 초안

1. 이벤트 서버 확인 상태
   - `POST /api/entry/{invite}/proctor-events`는 지금처럼 `snapshot`을 받고 즉시 `201`을 준다.
   - 서버가 비동기로 모델을 돌려 이벤트에 `serverCheck: PENDING | CONFIRMED | UNCONFIRMED`, `serverCheckedAt`을 붙인다.
   - 콘솔 `ProctorEventView`에도 두 필드를 추가한다.
2. 화면 공유 사진: `source=SCREEN` 추가. 흐림 처리를 클라이언트/서버 중 어디서 할지 합의 필요.
3. 감독관 영상 시그널링 (WebSocket `/ws/proctor` 확장)
   - 감독관 → 서버: `watch { participantId }`, `unwatch`
   - 서버 → 응시자: `viewer-request { channel }`
   - 응시자 → 서버 → 감독관: 채널별(휴대폰, 웹캠, 화면) `rtc` offer/answer/candidate 중계
   - 서버는 `rtc`를 해석하지 않고 전달만 한다. 감독관 권한 확인 필요.
   - **5단계 구현으로 확정된 메시지** (프론트·개발 릴레이 완료): `watch { sessionId, participantId }` · `unwatch` · `watch-state` · `viewer-request { viewer, channel }` · `viewer-gone` · 채널별 `view-rtc` (offer/answer/candidate/request/unavailable). 휴대폰 영상은 응시자 PC가 받은 것을 그대로 중계한다. 응시자 1명당 감독관 상한 2명(`watchRoom.ts` 한곳). 상세와 백엔드 권한 요건은 `pAIr-docs/API/실전시험_감독_API.md` 6-11.
4. 운영 릴레이: 개발 릴레이와 같은 동작을 Spring WebSocket으로 구현. 1단계 이후 서버는 시그널링과 연결 상태만 맡고 폰 이벤트 저장은 맡지 않는다.
5. 연결 끊김 유형 확장: 웹캠 끊김, 화면 공유 끊김 `type` 추가.
6. 분석 중단 감지(제안): PC가 "분석 동작 중" 신호를 주기적으로 보내고, 끊기면 서버가 이벤트를 남긴다.

## 6. 위험과 대응

- (a) PC 부하: 채널마다 최소 간격을 따로 둔다(웹캠 5~10회/초, 휴대폰 영상 3~5회/초, 화면 공유는 분석 없이 이벤트 순간 사진만). 저사양 PC 점유율은 직접 측정하고, 부족하면 Web Worker 분리를 검토한다.
- (b) 시그널링: 열었을 때만, 한 명씩만 보므로 P2P로 충분하다. 응시자 1명당 감독관 허용 수만 정한다.
- (c) 재확인 모델: 이벤트 순간 사진 한 장이라 부하는 작다. 자체 서버 큐 처리와 클라우드 비전 API 중 백엔드와 선택해야 한다. 4단계의 가장 큰 미결 사항.
- (d) 책상 스캔: PC 감지로 확정. 남는 위험은 PC가 받는 영상 화질이며, 스캔 때만 고화질로 올려 대응한다.
- (e) 분석 조작: 응시자가 분석을 끄거나 막을 수 있다. 감독관 영상 시청, 서버의 사진 재확인, 브라우저 이벤트의 서버 기록, "분석 중단 감지"로 탐지하며 완전한 방어는 아니다.
- 추가: 현재 휴대폰 송신 화질(400kbps, 10fps, 절반 해상도)이 분석에 부족하다. 1단계에서 올리지 않으면 작은 물체 감지가 나빠진다.

## 7. 첫 구현 세션 브리프 (1단계)

목표: 휴대폰에서 분석을 빼고 영상만 보내게 하고, 그 분석을 응시자 PC가 받은 휴대폰 영상에서 한다. 의도 문서는 `docs/intent/proctor-client-analysis.md`.

선행: `relay-diagnose` 세션이 끝난 뒤 시작한다. 그 세션이 만든 `phoneStale.ts`·`relayLog.ts`·`frameBudget.ts`를 먼저 읽는다.

할 일
1. `PhoneCamPage.tsx`에서 손·물체 모델 로딩(`loadMonitoringModels`), 분석(`makeAnalyzer`, `runMonitoring`), 보정(`runCalibration`)을 제거한다. 카메라 열기, 영상 송신, 상태 신호, 화면 이탈 알림만 남긴다. 책상 스캔은 2단계에서 옮기므로 이번에는 그대로 둔다.
2. `peerLink.ts`의 송신 화질을 분석이 가능한 값으로 올린다(예: 1~1.5Mbps, 15fps, 해상도 축소 없음). 휴대폰이 모델을 안 돌리므로 낮출 이유가 없다.
3. `camHub.ts`에 `phoneStream`을 입력으로 하는 휴대폰 분석 루프를 추가한다. 손·물체 모델은 기존 `models.ts` 로더를 쓰고, 규칙은 `phoneRules.ts`·`RuleEngine.ts`를 그대로 쓴다. 웹캠 분석과 프레임 예산을 따로 둔다.
4. 휴대폰 이벤트는 PC가 `source=PHONE_CAM`으로 자기 아웃박스(`camOutbox.ts`)에 넣어 저장한다. `proctorRelay.ts`의 `violation` 저장 경로는 제거한다. `PHONE_DISCONNECTED`처럼 서버가 만드는 이벤트는 그대로 둔다.
5. 보정(기준 위치 잡기)은 PC에서 3초 보정으로 옮긴다.

완료 기준: 휴대폰에 모델 다운로드·추론이 없고, PC가 휴대폰 영상으로 손 이탈·휴대폰·책·다른 화면을 감지해 저장한다. 휴대폰 CPU·메모리와 1006 종료 재현 여부를 이전과 비교한다.

하지 않을 것: 책상 스캔, 화면 공유, 서버 재확인, 감독관 영상.

검증: 규칙·보정 로직 단위 테스트, 빌드, 실제 휴대폰으로 감시 10분 이상.
