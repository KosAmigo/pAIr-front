# pAIr 역할 분담

> 2026-11-19 갱신. [기획_결정사항.md](기획_결정사항.md)과 [기술검증_보고서.md](기술검증_보고서.md) 반영, 주인이 없던 기능 배정(맨 아래 표)

## 전체 흐름과 담당

```
[팀원 1] 가입·로그인 ─ 회사 분리 ─ 크레딧 ─ 요청 제한 ─ 채점 큐 ─ 모니터링 ─ 배포
                                                   │
[팀원 3] 과제 선택 → 코드 편집 → Docker 실행 → AI 채팅 → 제출 ─┤→ 복기 트리
                                                   ↓
[팀원 2]                              채점 큐에서 꺼냄 → 이중 판정 + RAG → 리포트 → 대시보드
                                                   ↑
[팀원 4] 회사 담당자: 회차 생성 → 초대 메일 → 입장·환경 점검 → 감독 → 자동 제출 → 회차 결과 분석
```

| 팀원 | 흐름 | 대표 기능 | 맡는 테이블 |
| --- | --- | --- | --- |
| **1** | 플랫폼 (모든 요청이 지나가는 길) | 멀티테넌시 인증, Redis 채점 큐 | companies, users, company_inquiries, company_invites, credit_ledger, credit_purchases (+ Redis) |
| **2** | 결과 (제출 이후 → 리포트) | LLM 이중 판정 채점, RAG | 채점 기준·결과 10개, 문항 6개, 문서 2개 |
| **3** | 응시 (과제 선택 → 제출 → 복기) | Docker 샌드박스, 복기 트리 | tasks, task_files, attempts 외 응시 7개 |
| **4** | 실전 시험 (기업이 열고 → 결과 확인) | 시험 진행 + 감독, 회차 결과 분석 | exam_sessions, exam_session_tasks, exam_participants, proctor 2개 |

## 공통

### 흐름 사이 연결 (정해진 지점에서만 넘김)

| 지점 | 주는 쪽 → 받는 쪽 | 미리 정할 것 |
| --- | --- | --- |
| 로그인한 사용자 정보 | 1 → 전원 | 현재 사용자·회사를 꺼내는 공통 방법 |
| 응시 DB | 3 → 2, 4 | 응시·대화·파일 조회 방법 |
| 제출 → 채점 | 3, 4 → 1 → 2 | 채점 요청 형식(응시 ID, 버전), 결과 상태값 |
| 채점 결과 → 리포트 | 2 → 4 | 회차 결과 분석이 쓰는 점수 조회 |
| 응시 화면 안의 부품 | 2, 4 → 3 | 문항 패널(2), 감독 오버레이(4)를 끼우는 자리 |
| AI 호출 제한 | 1 → 3 | 제한에 걸렸을 때의 응답 형식 |
| 크레딧 차감 | 1 → 3 | 응시 시작·롤백·채팅 턴 차감 API, 잔액 부족 응답 형식 |
| 메일 발송 | 4 → 1 | 초대·인증 메일이 쓰는 공통 발송 모듈 |
| 파일 저장(S3) | 1 → 3, 4 | 과제 파일, 대상자 CSV, 감독 스냅샷 저장 방법 |
| 과제 생성 → 과제 콘솔 | 2 → 4 | AI가 만든 과제·문항을 HIDDEN으로 저장하는 형식 |

### 진행 순서

1. **기반:** 1의 로그인, 3의 응시 DB 전환. 이 둘이 끝나야 나머지가 DB 위에서 돕니다.
2. **각자 핵심:** 2는 채점 DB 전환과 RAG, 3은 Docker 샌드박스, 4는 회차와 입장, 1은 채점 큐와 크레딧
3. **흐름 연결:** 자가진단과 실전 시험이 응시부터 리포트까지 끝까지 도는지 확인
4. **대표 기능 2번째 + 확장:** 복기 트리, 감독, 비용 최적화, 웜 풀, 모니터링
5. **측정:** 각자 "보여 줄 숫자"를 실제로 측정해 포트폴리오와 발표 자료에 넣기

### 모두 지킬 것

- 맡은 기능의 테스트 코드는 본인이 작성합니다. 특히 권한, 격리, 큐 재시도는 테스트가 곧 포트폴리오 증거입니다.
- ERD 변경은 한 사람이 관리합니다. 스키마 파일 하나로만 바꿉니다.
- "보여 줄 숫자"는 측정 방법과 결과를 README에 남깁니다. 면접에서 그대로 쓰게 됩니다.

## 팀원 1: 플랫폼 흐름

**사용자 입장:** 가입하고 로그인하면, 내 권한과 회사에 맞는 데이터만 보입니다. 사람이 몰려도 서비스가 멈추지 않습니다.

| 구분 | 내용 |
| --- | --- |
| 화면 | 로그인, 가입(이메일 인증), 마이페이지(정보 수정, 탈퇴, 크레딧 잔액·구매), 기업 도입 문의 폼, 초대 링크 가입, 관리자 회사 콘솔(문의 승인, 담당자 초대) |
| API | 가입·로그인·토큰 재발급·로그아웃, 이메일 인증, 내 정보, 도입 문의·승인, 담당자·감독관 초대, 크레딧 잔액·차감·구매 |
| 인증 | Spring Security + JWT(액세스·리프레시), 로그아웃한 토큰은 Redis 차단 목록, BCrypt |
| 멀티테넌시 | 권한 4종(USER/MANAGER/PROCTOR/ADMIN), RoleHierarchy MANAGER > PROCTOR, ACTIVE만 로그인. 담당자의 모든 조회에 "내 회사" 조건이 자동으로 붙는 공통 처리(필터나 AOP). 다른 사람·다른 회사 데이터 요청은 403 |
| 크레딧 | 가입 시 지급, 원장(사유·응시·양·시각) 기록, 동시 차감에도 음수 안 되게 회원 행 잠금, 테스트 결제(결제 대행사 테스트 모드) |
| Redis 채점 큐 | 제출 → 큐에 넣기 → 작업자가 꺼내 팀원 2의 채점 엔진 호출. 실패 시 재시도(최대 N회 후 실패 보관함), 서버를 재시작해도 남음, 동시 작업 수 설정 |
| 호출 제한 | Redis로 사용자별·전체 분당 AI 호출 수 제한 (팀원 3의 채팅이 사용) |
| 인프라 | Docker Compose(백엔드, 프론트, PostgreSQL, Redis), GitHub Actions(테스트 → 빌드 → 배포), AWS(백엔드) + Oracle(실행 서버) 배포, S3 파일 저장 |
| 정책 | 탈퇴 시 개인정보만 익명화, 응시·채점 기록 1년 보관, 감사 추적 |
| 확장 | Prometheus + Grafana(응답 시간, 큐 길이, 회차별 AI 비용, 알림), 블루그린 무중단 배포 |

**포트폴리오 포인트**

- **실전 시험 종료 순간 채점 몰림 해결**
  - 문제: 100명이 동시에 제출하면 채점 100건(건당 약 50초)이 몰리고, 서버 메모리에만 있으면 재시작할 때 사라짐
  - 해결: Redis 큐, 재시도, 실패 보관함
  - 보여 줄 숫자: 부하 테스트(k6 등) 동시 제출 100건에서 유실 0건, 전부 처리될 때까지 걸린 시간
- **회사 간 데이터 완전 분리**
  - "개발자가 조건을 빠뜨려도 새지 않게" 공통 처리로 강제했다는 설계 이야기
  - 다른 회사 데이터 접근 차단 테스트 코드
- **크레딧 동시 차감:** 동시에 여러 번 차감해도 잔액이 음수가 되지 않는 테스트
- **운영 관점:** 대시보드로 회차 1회 AI 비용과 큐 대기 시간을 실시간으로 보여 줌, 배포 자동화
- **면접 예상 질문:** JWT를 쓰면서 로그아웃은 어떻게 처리했나, 큐에서 같은 채점이 두 번 실행되지 않게 어떻게 막았나, 크레딧 동시 차감은 어떻게 막았나

## 팀원 2: 결과 흐름

**사용자 입장:** 제출하면 몇 분 안에 6개 역량 점수와 "왜 감점됐는지" 근거가 담긴 리포트가 나오고, 내 점수 추이를 볼 수 있습니다.

| 구분 | 내용 |
| --- | --- |
| 화면 | 리포트(항목별 점수, 감점 근거 대화 인용, 문항 점수, 감독 주의 구간), 리포트 공유 링크(켜기·끄기, 읽기 전용 공유 화면), 개인 대시보드(역량 추이 차트), 내 기록, 비개발 문항 패널(객관식·단답형), 관리자 AI 과제 만들기 |
| API | 채점 실행(큐 작업자가 호출), 리포트 조회, 공유 링크, 대시보드 통계, 문항 답변 저장, AI 과제 생성 |
| 채점 엔진 | Spring AI로 Claude + GPT 두 모델 판정 → 평균, 구조화 출력(JSON Schema), 근거 턴이 없는 감점은 무효, 단답형은 코드로 자동 채점. JSON 파일 저장을 DB로 전환 |
| RAG | PDF 페이지 텍스트 추출 → 조각 나누기 → OpenAI 임베딩 → pgvector(HNSW) 검색 → 채점 프롬프트에 근거 조각만 넣기 |
| AI 과제 생성 | 관리자가 폼(직군, 난이도, 주제, 함정)으로 정의 → AI가 과제·문항 생성 → HIDDEN으로 저장, 팀원 4의 과제 콘솔에서 검수 후 공개 |
| 채점 툴 | 프롬프트 버전 관리, 반복 채점 편차 검증(이미 있음, DB 연결), 채점 비용 추적 |
| 확장 | 비용 최적화(쉬운 체크는 작은 모델로 보내는 모델 라우팅, 프롬프트 캐시, Batch API), 맞춤 학습 피드백(감점 패턴 → 다음 질문 방법·과제 추천) |

**포트폴리오 포인트**

- **LLM 채점의 흔들림 줄이기**
  - 문제: 같은 응시를 다시 채점해도 4~8점씩 바뀜
  - 해결: 두 회사 모델 평균, 판정 기준 문장 개선, 근거 강제
  - 보여 줄 숫자: 반복 채점 편차 8점 → 3점 이내. 채점 툴로 측정한 실험 기록이 그대로 증거
- **RAG 설계 판단**
  - "숫자 표는 RAG보다 통째로 넘기는 게 낫다"를 실험으로 확인하고 문서 종류별로 다르게 처리
  - 보여 줄 숫자: 검색 정확도(상위 3개 안에 정답 조각)
- **비용:** 채점 1건 비용을 몇 % 줄였는지(정확도는 유지)
- **면접 예상 질문:** LLM이 지어낸 감점은 어떻게 걸렀나, 왜 모델 두 개를 썼나, 임베딩 차원과 인덱스는 왜 그렇게 골랐나

## 팀원 3: 응시 흐름

**사용자 입장:** 과제를 골라 브라우저에서 코드를 고치고 실행하고, AI에게 물어보며 풀고, 제출합니다. 끝난 뒤에는 원하는 시점으로 돌아가 다르게 풀어 볼 수 있습니다.

| 구분 | 내용 |
| --- | --- |
| 화면 | 과제 목록, 응시 화면(코드 편집기, 파일 트리, 자동 저장, 실행 결과, AI 채팅 패널, 첨부, 후속 질문), 복기 트리 화면 |
| API | 응시 시작·저장·빌드·실행·채팅·제출, 체크포인트 생성, 롤백 |
| 응시 DB 전환 | 응시, 작업 파일, 대화, 작업 기록을 JSON 파일에서 DB로 (**가장 먼저**, 다른 흐름이 이 위에 붙음) |
| Docker 샌드박스 | Oracle 실행 서버에서 응시마다 격리 컨테이너로 javac 빌드·실행. 네트워크 차단, CPU·메모리 제한, 읽기 전용 파일시스템, 30초 강제 종료, 지정 파일만 수정 가능, 작업 폴더 용량 제한, 응시자 배정(응시마다 실행 서버 기록) |
| 편집기 IDE 기능 | CodeMirror + javac API로 실시간 오류 밑줄, 자동 완성, 정의로 이동 |
| AI 채팅 | 스트리밍 응답(첫 글자부터 표시), 파일 첨부(과제 자료, 내 작업 파일만)와 토큰 제한, AI 수정 제안 적용·거절(새 파일 만들기는 막음), 크레딧이 바닥나면 채팅만 막기 |
| 복기 트리 | 특정 대화 시점의 파일·대화를 저장(체크포인트) → 그 시점에서 갈라진 새 응시 생성 → 트리로 표시, 롤백마다 크레딧 차감(횟수 제한 없음), 두 갈래 점수 비교 |
| 확장 | 컨테이너 웜 풀(미리 띄워 두고 재사용), 빌드·실행 출력 실시간 스트리밍(WebSocket) |

검증 근거: `poc/sandbox/`(격리, 롤백, 지정 파일), `poc/javac-api/`(IDE 기능), [기술검증_보고서.md](기술검증_보고서.md) 7~10번

**포트폴리오 포인트**

- **남의 코드를 안전하게 실행하기**
  - 문제: 응시자 코드를 서버에서 그대로 돌리면 무한 루프, 파일 삭제, 외부 접속 위험
  - 해결: 컨테이너 격리와 자원 제한
  - 보여 줄 숫자: 악성 코드 시나리오(무한 루프, 포크 폭탄, 외부 접속, 파일 삭제) 차단 결과표
- **성능:** 웜 풀 적용 전후 실행 대기 시간(예: 2초 → 0.3초), 동시 실행 몇 개까지 버티는지
- **복기 트리 설계**
  - 상태를 통째로 복사하지 않고 "시점 + 바뀐 파일"만 저장하는 방식
  - 트리 자료구조와 시각화
- **면접 예상 질문:** 컨테이너 탈출은 어떻게 막았나, 스트리밍 중에 연결이 끊기면 어떻게 되나, 롤백할 때 대화는 어디까지 복사하나

## 팀원 4: 실전 시험 흐름

**사용자 입장:** 기업 담당자가 회차를 열고 지원자를 초대합니다. 지원자는 감독을 받으며 같은 시각에 시험을 보고, 담당자는 결과와 부정행위 의심 구간을 한눈에 봅니다.

| 구분 | 내용 |
| --- | --- |
| 화면 | 기업 관리자(회차 생성·수정·취소, 대상자 CSV 업로드, 진행 현황), 실전 입장(메일 링크 → 시험 정보 → 환경 점검·동의 → 대기), 감독 오버레이(카메라 미리보기, 경고), 제출 완료, 회차 결과 분석, 관리자 과제 콘솔(목록, 검수·편집, 응시자로 보기), 초기화면 |

**포트폴리오 포인트**

- **개인정보를 지키는 감독 설계**
  - 문제: 영상을 서버로 보내면 트래픽, 저장 공간, 개인정보 부담이 큼
  - 해결: 브라우저에서 분석하고 사진 1장만 전송, 얼굴로 사람을 식별하지 않음(생체정보 아님), 보관 기간이 지나면 삭제
  - 보여 줄 숫자: 영상 전송 대비 줄어든 데이터 양
- **오탐률을 숫자로 관리:** 조건별 오탐률표와 기준값 조정 전후
- **동시 시작·종료:** 시계가 틀린 기기도 공정하게 서버 시각 기준으로 처리, 종료 순간 자동 제출의 정확성
- **면접 예상 질문:** 브라우저 감지는 응시자가 끌 수 있지 않나, 오탐이 나면 어떻게 하나, 응시자 1,000명 회차 통계는 어떻게 빠르게 뽑나
